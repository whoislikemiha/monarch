# MON-103 — Quest-close Keeper trigger

Linear: [MON-103](https://linear.app/monarch-commander/issue/MON-103/p2-keeper-quest-close-trigger-deeper-distillation-pass)
Plan: [thoughts/plan/MON-103.md](../plan/MON-103.md)

## What shipped

Quest close is now a Keeper trigger alongside continuous token-pressure compaction:

1. **Status transition handling.** `db_update_quest` reads the quest before/after update, records a `status_change` event when the status changes, and treats `not done -> done` as a semantic close.
2. **Current quest cleanup.** On close, `agents.current_quest_id` is cleared only if it still points at the closed quest. The next meaningful turn can therefore auto-create a fresh quest without disturbing newer work.
3. **Keeper trigger generalization.** `AgentManager::dispatch_keeper_run` now accepts a `KeeperRunTrigger`. Continuous runs stay anchored to the last successful Keeper run; quest-close runs are anchored to `quest.started_at ?? quest.created_at`.
4. **Run provenance.** `memory_keeper_runs` stores `trigger='quest_close'` and the closing quest id. `keeper_run` commands also carry `trigger` so the sidecar can branch on prompt/model later.
5. **Result attribution.** `keeper_result` handling reloads the run row and uses its quest id for memory `source_quest_id` and `compaction_tick`, so an async Keeper result cannot attach to a later auto-created quest.
6. **Timeline UI.** Expanded non-done quests show Mark done. Compaction ticks render their trigger label (`continuous` or `quest close`).
7. **Docs.** ONBOARDING now documents the `keeper_run.trigger` contract and quest-close lifecycle.

## Notes

- If `memory.toml` has no Keeper model, marking a quest done still persists the status and timestamp. Keeper dispatch returns a silent no-op.
- WebSocket fallback mirrors the Tauri `db_update_quest` side effects.
- The first version intentionally reuses the continuous Keeper prompt/model. Separate quest-close model tiering and deeper prompt calibration stay deferred until eval signal exists.
