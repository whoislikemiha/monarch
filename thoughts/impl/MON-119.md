# MON-119 — P6 Slice A implementation notes

## What was implemented

Backend substrate for P6 first-person quest reports. Monarch now has a
`quest_reports` table, a Tauri command surface that the captain (Slice C)
and tests can drive, and a `PersistCommand` variant that Slice B's
sidecar `complete_quest(report)` tool will route through. No producer
exists in Slice A — the rest of P6 has somewhere to attach.

## Key decisions

- **One report per quest** via `UNIQUE (quest_id)` and a single
  `upsert_quest_report_internal` helper that handles both first-write
  and revisions through `INSERT ... ON CONFLICT(quest_id) DO UPDATE`.
  Simpler than separate insert/update helpers; the Slice B tool stays
  a single call regardless of whether the executor is writing a draft
  or revising one.
- **`agent_id` resolved server-side, not by callers.** The upsert
  helper reads `quest_nodes.assignee_shadow_id` for the supplied
  `quest_id` and stores it on the row. Callers never pass an
  `agent_id`. This keeps the denormalized column honest — no way for
  a stale value to drift in from a caller.
- **Two write paths, same internal helper.** Captain saves go through
  `db_save_quest_report` (Tauri command, direct write); sidecar saves
  in Slice B will go through `PersistCommand::WriteQuestReport`
  (pipeline). Both call `upsert_quest_report_internal` and emit on
  `quest-report-{quest_id}`. Matches the `quest_refs` vs
  `quest_events` precedent already established by P5 / MON-100.
- **Agent-archive symmetry.** `agent_id` uses `ON DELETE SET NULL` to
  match `quest_nodes.assignee_shadow_id`. When an agent disappears the
  report stays attached to the quest but loses attribution — same
  lossy-preserved pattern.
- **CLAUDE.md backfill folded into the slice** rather than left as a
  follow-up. The post-launch schema list had drifted across nine tables
  and five columns spanning six earlier tickets; one paragraph edit
  catches all of them.

## Files touched

- `src-tauri/src/db.rs` — schema block, `QuestReportRow` /
  `WriteQuestReportPayload` DTOs, the three `*_internal` helpers,
  three `#[tauri::command]` wrappers, `emit_quest_report_notification`
  helper, `map_quest_report` row mapper, and the six new tests at the
  bottom of the test module.
- `src-tauri/src/agent/persist.rs` — `WriteQuestReport` variant,
  `agent_id()` arm, and apply arm broadcasting on
  `quest-report-{quest_id}`.
- `src-tauri/src/lib.rs` — three new command names in both the runtime
  handler list and the export-bindings list.
- `src-tauri/src/ws.rs` — three new WebSocket dispatch arms.
- `src/lib/bindings.ts` — regenerated by `cargo run -- --export-bindings`.
- `CLAUDE.md` — post-launch schema list backfill.

## What was left out

- **Sidecar `complete_quest(report)` tool** and the executor system-prompt
  block that teaches the structured payload shape — Slice B (next).
- **Captain UI / renderer** in the P5 quest detail panel — Slice C.
- **Keeper input pipeline change** — `quest_reports.payload` is not yet
  consumed by Keeper ticks on quest close; today's Keeper still reads
  only the raw event stream slice. Slice D.
- **Quest status enforcement** — closing a quest without a report still
  succeeds. The "report-on-close" contract will be enforced by Slice B's
  prompt + tool semantics, not by the schema.
- **No frontend consumer of the new commands** yet — `dbSaveQuestReport`,
  `dbGetQuestReport`, and `dbListQuestReportsForAgent` are exported but
  unused until Slice C.
