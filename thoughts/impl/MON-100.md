# MON-100 — P2 Slice B: Keeper write path (continuous compaction)

## What was implemented

The continuous-compaction loop. The Keeper now distills the executor's recent activity into atomic claims AND collapses Pi's `state.messages` to a synthesized scaffold every ~30k tokens of accumulated usage. Memory formation and context compaction are the same operation, observable in the chat thread via two status rows ("Keeper distilled N memories" → "Context compacted").

Before this slice, the substrate from MON-99 had the schema, embedder, HNSW, and Inspector v0 in place but no writer. Slice B is the writer. After this slice the executor's context window stops growing past the configured threshold (default 30k); the captain sees memories accumulate in the Inspector and watches compactions land in the chat as they happen.

## Key decisions

- **Token counter sums `input + output + cacheRead + cacheWrite`** explicitly rather than trusting `usage.totalTokens`. The Anthropic 200k cache-read window is real loaded context for the LLM and we want it counted. Side effect: a Sonnet conversation with heavy cache reuse triggers compaction at 25-30k of accumulated context, not 25-30k of fresh content — which is the desired behaviour.
- **No `compaction_pending` flag on the live state.** Equivalent to checking `tokens >= soft_threshold` inline at `TurnEnd`. One less piece of state to keep coherent.
- **No separate `RewriteMessages` Rust command.** Folded into the sidecar's `keeper_run` handler — the sidecar already has the slice, the summary, and direct access to `state.messages`. Saves a round trip; plan permitted this.
- **Rewrite drains at `turn_end`, not `agent_end`.** Originally deferred to `agent_end` to avoid mid-LLM-call mutation, but `agent_end` only fires once per prompt cycle. For long "prime on the codebase" tasks that run dozens of turns under one prompt, every keeper tick stashed a pending rewrite that overwrote the previous one without ever applying. `turn_end` fires between LLM calls (during tool execution) — safe, and frequent enough that rewrites land mid-task.
- **Internal dispatch channel** instead of refactoring `ensure_sidecar` / Tauri commands to thread `Arc<Self>` through every callsite. The event handler enqueues `InternalDispatch::KeeperRun { agent_id }`; a manager-owned consumer task drains via `Arc<Self>`. Localized change.
- **Live-state mutation lives in the event handler**, not in a `PersistCommand` variant. Persist consumer stays DB-only; live counter reset + in-flight clear happen inline in `handle_keeper_result` before the persist commands enqueue.
- **`InsertMemory.apply` embeds via `MemoryIndex::embed_to_blob` before insert.** If the embedder is not initialised, the row is still written without an embedding — FTS5 retrieval keeps working, only the HNSW vector path is skipped until the next rebuild after init.
- **Slice cap walks newest-first** with a 30k-token budget; a single oversized message gets pushed whole (we don't split). Acceptable for Anthropic-class models (200k+ context). Smaller local models could choke on a 100k single-turn slice — flagged as a follow-up hardening (cap individual rendered message content + always include the most recent user message).
- **Keeper system prompt lives in code** (`memory_config::DEFAULT_KEEPER_SYSTEM_PROMPT`), not in `memory.toml`. Settings UI surfaces it read-only via `ResolvedMemoryConfig.keeper_system_prompt`. Captain-edited prompt is out of scope; same pattern as the classifier.
- **Visible status rows** (`◈ Keeper distilled N memories` + `✦ Context compacted`) are the captain's primary observability surface. Stderr telemetry + `memory_keeper_runs` rows are the secondary. Quest Timeline's `compaction_tick` only appears when the agent has a current quest.

## What was left out

- **Slice-cap hardenings** for tiny Keeper models: always include the most recent user message in the slice; truncate any individual rendered message content to ~5-10k chars. Anthropic-class models (200k+) handle the 100k single-turn case fine, so deferred until a captain trips over it with a local-only Keeper.
- **`source_events` provenance on memories** — currently shipped as `None`. The substrate already records raw events in `events` and the slice rendering is deterministic from `last_keeper_run.completed_at`, so this is informational. P3+ populates it once we want fine-grained replay.
- **Idle compaction trigger** — small follow-up after this lands. Same Keeper, idle-timer dispatch.
- **Quest-close semantic trigger** — split into MON-103. Reuses this slice's plumbing; adds status-transition detection + a "Mark done" UI affordance.
- **Hybrid retrieval / `## Relevant Memories` injection on user turn** — Slice C / MON-101.
- **Executor `suggest_memory` tool** — MON-102.
- **Pi's built-in `compact()` override** — left untouched for v1. Anthropic's 1M context lands well past 30k so its auto-compact won't fire in practice.
- **Single-turn-blows-30k corner** — if one turn produces 30k+ tokens with no `MessageEnd`, neither trigger fires. Out of v1; add `ToolExecutionEnd` checks later if needed.
- **`keeper_in_flight` stuck on sidecar death** — if the sidecar dies mid-run, the flag stays true until Monarch restart (`keeper_in_flight` is `#[serde(skip)]` so cold-start defaults it to `false`). Acceptable — Monarch restart is the recovery path.
- **Explicit Keeper-call timeout.** Classifier has 3s; Keeper does deeper work and shouldn't hard-cap. Anthropic API timeouts cover the worst case for v1.
