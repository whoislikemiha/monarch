# MON-112 — P4b Slice B implementation notes

## What was implemented

Sidecar layer that lets the executor declare and operate a durable per-quest plan via custom tools, plus the prompt guidance that teaches when to use them. Slice A's persistence pipeline accepts the events as-is — no Rust changes in this slice.

## Key decisions

- **Five tools, not six.** `update_plan` (diff-style) was deferred per Q1 in the design discussion. `set_plan`'s replace-by-id semantics already cover reorder / insert / edit / remove without a second tool surface. The simpler executor mental model is "declare or replace the plan; mutate by id."
- **camelCase wire fields.** Rust uses serde `rename_all_fields = "camelCase"` on the inner-event enum, so the JSON keys must be `previousOutcome`, `itemId`, etc. Confirmed by a local probe before writing plan-tools. This caught a pre-existing MON-108 bug — `narration-tools.ts` was sending `previous_outcome` and the field was silently `None` in prod. Drive-by fixed in the same PR.
- **Optional `item_id` on skip / block.** Matches the executor's mental model that the live plan slice is the implicit subject. The persist pipeline already resolves the active item server-side via `get_active_plan_item_for_agent_internal` when `item_id` is omitted.
- **Soft length caps with ellipsis truncation.** Mirrors the narration-tools pattern. A plan tool call should never fail because a title is too long — the executor's intent should land, just trimmed.
- **Defensive empty-string guards on required params.** Pi's parameter validation accepts empty strings even when the schema types them as required. Both branches return matching `details` shapes so TS inference is happy.
- **Prompt block lives inside `buildSystemPrompt`**, not a separate injection mechanism. The oath already owns the full prompt; the new `## Execution Plan` section sits after `## Action Narration` so the two narration surfaces are co-located.

## Files touched

- `sidecar/src/plan-tools.ts` (new) — `createPlanTools(agentId, emit)` factory, five `defineTool` entries.
- `sidecar/src/runtime-manager.ts` — import + spread `createPlanTools(...)` into `customTools` at `createAgentSession`.
- `sidecar/src/shadow-oath.ts` — five new tool entries in the inline tool list, new `## Execution Plan` section with intent/granularity/revision guidance + one worked end-to-end example.
- `sidecar/src/narration-tools.ts` — drive-by fix: `previous_outcome` → `previousOutcome` on the wire so the field is no longer silently dropped.

## What was left out

- **Plan panel UI, timeline plan-item chips, Now-strip extension** — Slice C (MON-113).
- **Diff-style `update_plan`** — see Decisions; bulk replace covers it.
- **Strict status transition guards** — DB still allows e.g. blocking a completed item; CHECK only validates final value. Future refinement if executor proves to need it.
- **Provider-specific tool gating** — none. All five tools register for every executor session regardless of model/provider.
- **Tests** — Slice B is sidecar TS only; no automated coverage was added. Manual smoke (boot the app, drive a small refactor, watch DB) is the verification path. If we want sidecar unit tests for the JSON shapes, that's its own ticket.
