# MON-100 — P2 Slice B: Keeper write path (memories form at quest-close)

> **Sibling slices.** Slice A ([MON-99](https://linear.app/monarch-commander/issue/MON-99), shipped on master) ships the substrate: `memories` / `memories_fts` / `memory_keeper_runs` schema, embedding pipeline, HNSW index, Memory Inspector v0, debug-only `memory_smoke_insert`. Slice C ([MON-101](https://linear.app/monarch-commander/issue/MON-101)) wires retrieval into the user-turn path. **Slice B (this ticket) wires the write half:** quest-close → sidecar Keeper → memory rows + `compaction_tick` quest event, plus an executor `suggest_memory` tool that queues proposals for the Keeper to consider. No reader yet — Slice C is the first consumer.

## Summary

When a quest's `status` transitions to `done`, Rust dispatches a one-shot `keeper_run` command to the long-lived sidecar with the agent id, quest id, and a slice of the quest's raw events / messages. A new `sidecar/src/keeper.ts` worker — modelled on `classifier.ts` — invokes `complete()` once against the configured Keeper model with a structured-JSON system prompt and returns `{ claims, compaction_summary }`. The sidecar emits a `keeper_result` event; Rust's existing event handler enqueues `PersistCommand` variants on the single-consumer pipeline that (a) insert each claim into `memories` (carrying `source_quest_id` / `source_session_id` / `source_events` provenance), (b) finalize the matching `memory_keeper_runs` row, (c) record one `compaction_tick` row in `quest_events`, and (d) trigger an HNSW rebuild after the inserts settle. The executor session also gets a new `suggest_memory(title, summary, content)` tool whose calls fan out to a `memory_suggestion` quest event — ordinary `quest_events` content the Keeper sees naturally on its next pass. If `memory.toml` has no Keeper model configured, the trigger is a silent no-op so users not opted into memory pay zero cost.

## Relevant files and areas

### Wire protocol
- `sidecar/src/protocol.ts` — add `KeeperRunCommand` (Rust→sidecar) plus `KeeperResultEvent` (sidecar→Rust). Mirror in `src-tauri/src/sidecar_protocol.rs` (`SidecarCommand::KeeperRun`, `SidecarEvent::KeeperResult`, plus a `KeeperConfig` substruct analogous to `ClassifierInvocationConfig`). Extend `KNOWN_SIDECAR_TAGS` so the new variant doesn't fall to `Unknown`.

### Sidecar (worker + trigger handler)
- `sidecar/src/keeper.ts` *(new)* — one-shot runner. Same shape as `sidecar/src/classifier.ts`: resolves model + auth via `session.modelRegistry`, calls `complete()` with the Keeper system prompt + a serialized event slice, parses JSON output, never throws — returns either `{ claims, compaction_summary, model, latencyMs, ... }` or `{ error, model?, latencyMs }`. Shipped pieces of config (provider/model/timeout/system prompt) come down from Rust on each invocation, like the classifier.
- `sidecar/src/runtime-manager.ts` — handle the new `keeper_run` SidecarCommand: pull the managed session for the agent (purely to reuse `modelRegistry` for auth), invoke `keeper.run(...)` with the supplied event slice, emit one `keeper_result` event. Independent of any in-flight Pi turn — does not block, does not interleave with the executor's stream.
- `sidecar/src/runtime-manager.ts` (executor extension surface) — register a `suggest_memory` tool that the executor can call. Mechanism is the open question (#2 below); the contract is that calling the tool produces a `memory_suggestion` event Rust can route into `quest_events` rows.

### Rust trigger + event handling
- `src-tauri/src/db.rs` — `update_quest_internal` already supports status writes but does not auto-record events. The trigger needs to live one layer up so it has the *previous* status to compare against. Either (a) extend the existing `db_update_quest` Tauri command in this file, or (b) introduce a thin `quest_close(quest_id)` Tauri command that does the read-old-status-then-write-new-status-then-fire-keeper dance atomically. Either way: when status flips from any non-`done` state to `done`, build a `KeeperRunCommand` and forward to the sidecar via the existing stdin pipe.
- `src-tauri/src/agent/sidecar.rs` — already exposes the stdin pipe. The new variant flows through unchanged once `SidecarCommand::KeeperRun` is added.
- `src-tauri/src/agent/event_handler.rs` — extend `handle_sidecar_event` with a `SidecarEvent::KeeperResult` arm. Build `PersistCommand`s analogously to `Classification` handling: one `InsertMemory` per claim, one `CompleteKeeperRun`, one `RecordQuestEvent` for the `compaction_tick`. Errors land in the persist consumer, which already flips the desync indicator.
- `src-tauri/src/agent/persist.rs` — add new variants:
  - `PersistCommand::InsertMemory { agent_id, payload }` — calls `insert_memory_internal` (already exists on `Database`); embeds the content via the shared `MemoryIndex` *before* the insert so the row carries an embedding blob.
  - `PersistCommand::CompleteKeeperRun { run_id, ... }` — calls `complete_keeper_run_internal` to fill in `completed_at`, `tokens_*`, `output_summary`, `outcome`.
  - `PersistCommand::RecordQuestEvent { quest_id, event_type, actor, payload_json }` — generic wrapper around `record_quest_event_internal` so `compaction_tick` and `memory_suggestion` can reuse the same path. (Current `quest_events` writes go through `db_create_quest` and a separate Tauri command; the Keeper / suggest paths need it from inside the sidecar event reader.)
  - On the `keeper_result` apply path, after the inserts settle, call into `MemoryIndex::rebuild` (already used by `memory_smoke_insert`). HNSW rebuild belongs in the persist consumer so it cannot race the inserts.
- `src-tauri/src/agent/manager.rs` — the `keeper_run` outbound command needs an entry point parallel to the existing `prompt`/`set_model` paths. Sketch: `AgentManager::dispatch_keeper_run(agent_id, quest_id, ...) -> Result<run_id>` that inserts the `memory_keeper_runs` row first (`outcome='pending'`), serializes a `SidecarCommand::KeeperRun` with the resolved Keeper config + event slice + run_id, and writes it to the agent's stdin. The trigger from `db_update_quest` calls into this.
- `src-tauri/src/memory_config.rs` — already carries the Keeper model. Add a `keeper_system_prompt` constant in the same module (mirroring `classifier_config.rs`'s `DEFAULT_CLASSIFIER_SYSTEM_PROMPT`) and surface it via `ResolvedMemoryConfig` so Rust ships the prompt to the sidecar on every run. Read-only at the UI layer for v1.

### Frontend
- `src/lib/toolbox/tools/QuestTimelineTool.svelte` — extend the event-log renderer to give `compaction_tick` and `memory_suggestion` rows distinct visual treatment. Nothing else needs to change in this slice — the existing per-root subscription to `quest-event-{rootId}` already wakes the store on new rows, and `db_list_quest_events` returns the new types unchanged.
- *(probably)* `src/lib/toolbox/tools/QuestTimelineTool.svelte` — add a "Mark done" affordance on the expanded detail panel so manual verification doesn't require devtools (open question #3).
- `src/lib/bindings.ts` — regenerated via `cargo run -- --export-bindings` once the new Rust commands land.

### Configuration
- `~/.config/monarch/memory.toml` — already loaded by `memory_config.rs` (Slice A). No file-format changes; the new `system_prompt` lives in code.

## What needs to change

### 1. Trigger surface — quest-close → keeper_run
- Detect the `status → done` transition at the `db_update_quest` Tauri-command boundary (or in a sibling `quest_close` command). The trigger must read the *previous* status row before writing the new one so we don't fire on every save of an already-done quest. Idempotency: only the first `→ done` flip enqueues a Keeper run.
- Skip the trigger when `ResolvedMemoryConfig.enabled` is false (no Keeper model configured).
- Insert a `memory_keeper_runs` row with `outcome='pending'`, `trigger='quest_close'`, populated `agent_id`/`quest_id`/`model_id`. Pass the row id along to the sidecar so the result can backfill it precisely.
- Build the event slice (open question #1) and ship it inside `SidecarCommand::KeeperRun`.

### 2. Sidecar Keeper worker
- New `sidecar/src/keeper.ts` modeled structurally on `classifier.ts`: timeout abort, `runProvider` helper, JSON parse with code-fence stripping, never throws.
- Distinct system prompt (Rust constant), input shape: a textual representation of the quest's event slice (raw `quest_events` rows + a window of `messages`), expected output shape: `{ claims: [{ title, summary, content, kind, file_refs?: [{path, anchor_sha}] }], compaction_summary }`. Detail of the schema gets locked in implementation; the field set must round-trip cleanly through `insert_memory_internal`.
- Failure → `keeper_result` event with `error` + `latency_ms`, no `claims` field.

### 3. Rust event-handler dispatch on keeper_result
- Add a `SidecarEvent::KeeperResult` arm to `handle_sidecar_event`. Persist via the existing single-consumer pipeline so the writes stay FIFO with everything else for that agent.
- Three classes of `PersistCommand` get enqueued per successful run: N × `InsertMemory`, 1 × `CompleteKeeperRun`, 1 × `RecordQuestEvent('compaction_tick')`. Embedding happens inside the `InsertMemory` apply (single-consumer makes it safe to share `MemoryIndex`). HNSW rebuild fires once at the tail.
- Failure path: `CompleteKeeperRun` with `outcome='error'` + the message, plus a `compaction_tick` payload that records the failure visibly on the timeline.

### 4. `compaction_tick` rendering
- `QuestTimelineTool.svelte` already iterates `events` per quest. Add a branch so `event_type === "compaction_tick"` renders with a distinct icon/color and the payload's `summary` inline. `memory_suggestion` likewise.
- No new event-channel wiring — the existing `quest-event-{rootId}` per-root listener already invalidates the cache.

### 5. `suggest_memory` executor tool
- New tool the executor's Pi session can call: `suggest_memory(title: string, summary: string, content: string)`. Calling it produces a sidecar inner event the Rust handler routes to `record_quest_event_internal` with `event_type='memory_suggestion'`, `payload_json = { title, summary, content }`, `actor = agent_id`. The Keeper sees these naturally next time it runs.
- Memory-poisoning firewall preserved: the executor *suggests*, the Keeper still decides whether to write. No direct path from `suggest_memory` to `memories`.
- The tool is registered into the executor session at `createSession` time (open question #2 — registration mechanism).

### 6. HNSW rebuild after each successful Keeper run
- Single full rebuild from `MemoryIndex::rebuild` after the last `InsertMemory` lands for a given run. Reuses the same code path the Slice A smoke command uses. Background rebuild + atomic swap is P3c (out of scope).

### 7. Silent no-op when memory is disabled
- `db_update_quest` reads `ResolvedMemoryConfig` once per status-change call. If `enabled == false`, skip the Keeper trigger but still write the status update normally. This is the captain's clean opt-out — useful for users who prefer the on-disk Anthropic auto-memory pattern as their L1 today.

### 8. Manual verification & bindings
- Regenerate `src/lib/bindings.ts` via `cargo run -- --export-bindings` once new Tauri commands land.
- Manual test: configure Keeper model in Settings → Memory; run a multi-turn task; mark the quest done; observe one `compaction_tick` event in `QuestTimelineTool` and one or more memories in the Memory Inspector with correct provenance (source quest id, keeper run id, source events). Restart cold; memories persist; HNSW rebuilds.

## Open questions

1. **Quest event slice — what does the Keeper actually consume?** Today `messages.quest_id` is NULL everywhere (per MON-83 plan: "Slice 2 leaves this NULL everywhere; Slice 3 (Architect) is the first writer"), and `quest_events` for a given quest currently only contains a creation `status_change` row. So the Keeper's "raw event slice" can't be sourced from those alone. Three options:
   - **(a) Bracket-by-time on session messages.** Use the agent's session messages whose `timestamp` falls between `quest_nodes.started_at` (or `created_at` if no `started_at`) and the current time. Pragmatic, no schema change. Risk: cross-quest bleed when an agent works on multiple quests in one session.
   - **(b) Backfill `messages.quest_id` from `agents.current_quest_id` at message-save time.** Cleaner attribution, but introduces a write that wasn't planned for Slice 2 (and was reserved for Slice 3 of MON-83). Crosses ticket boundaries.
   - **(c) Hybrid:** start with (a) for Slice B, with a sketch in the impl notes showing how (b) would replace it post-MON-84. Keeper eats whatever it gets.
   
   Recommendation: **(a)** with a clear caveat in the impl notes. Cleanest to revisit when MON-84 lands the Architect.

2. **`suggest_memory` registration mechanism.** Pi-coding-agent exposes `Extension`, `ExtensionFactory`, `ToolDefinition` types. Today Monarch passes `noExtensions: true` (and friends) to the resource loader to disable agent-local discovery, but `session.bindExtensions(...)` is still called. The likely path is to supply a Monarch-internal extension factory through `bindExtensions` (or `createAgentSession`'s extension list, depending on the SDK shape) that registers `suggest_memory` as a custom `ToolDefinition`. Implementation should verify against the actual `bindExtensions` signature in pi-coding-agent ≥ 0.70.2 — the Slice A SDK shim already had to chase shape drift, so this is non-trivial. If extension-side registration is awkward, fall back to a session-internal tool registration via the `SessionStartEvent` hook. Surface this in the impl notes once resolved.

3. **Mark-done UI affordance.** No "Mark done" button exists today in `QuestTimelineTool.svelte` — the only mutation is "create new quest" / "create sub-quest". To make Slice B testable without devtools, this slice probably needs to add a status dropdown or a "Mark done" button on the expanded detail panel. Tracking it in this ticket avoids a contortion in manual QA. Push back if the preference is to keep the UI changes minimal and verify via devtools / direct Tauri invoke.

4. **Keeper system prompt location.** The classifier ships its prompt as a Rust constant (`DEFAULT_CLASSIFIER_SYSTEM_PROMPT` in `classifier_config.rs`) and pipes it to the sidecar each turn. Same pattern here — Rust is canonical, sidecar is stateless. The plan assumes this; flagging only because the `distillation.md` design doc has not yet locked the exact prompt text. Initial prompt can be a short "extract atomic claims as JSON" baseline; eval-driven tuning lands in P3a.

5. **Run granularity and idempotency on re-saves.** If the captain saves a quest update with `status='done'` *while it's already done* (common — re-saving via the UI for an unrelated edit), do we re-fire the Keeper? Recommendation: trigger only on the *transition* (previous != 'done', new == 'done'). The trigger code reads the previous row in the same transaction it does the write.

6. **HNSW rebuild placement and back-pressure.** Doing one full rebuild per successful Keeper run is fine at P2 volumes (the MON-91 spike validated p99 < 6 ms at 1 M vectors), but in the persist consumer it serializes with all other agents' writes. If there's bandwidth concern, the rebuild can be a debounced fire-and-forget after the inserts; otherwise leave it inline in the consumer for ordering simplicity. Default to inline for v1.

7. **`source_events` payload shape.** `memories.source_events` is a TEXT column (per Slice A schema), unspecified content. Does the Keeper write a JSON array of `quest_events.id` strings, or an opaque "summary of the slice"? Recommendation: array of event ids so the Memory Inspector can drill into the originating events later (Slice C / P12 territory). Lock at impl time.
