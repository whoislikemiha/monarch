>
> **Sibling slices.** [MON-99](https://linear.app/monarch-commander/issue/MON-99) shipped the substrate (memories schema, FTS5, embedding pipeline, HNSW, Memory Inspector v0). [MON-101](https://linear.app/monarch-commander/issue/MON-101) wires retrieval (read path on user turn). [MON-102](https://linear.app/monarch-commander/issue/MON-102) adds the executor `suggest_memory` tool. **This ticket wires the continuous compaction loop** — token-pressure-triggered Keeper that produces memories AND replaces the executor's pre-tick raw conversation with a synthesized scaffold so context shrinks as memories form.

## Summary

Compaction and memory formation are the same operation. Every ~30k tokens of executor activity (sum of `usage.total_tokens` across `message_end` events since the last successful Keeper tick), the Keeper distills the recent stream into atomic claims and resets the executor's raw context window. Soft trigger at ~25k tokens looks for a natural breakpoint within ~5k more (next `turn_end` or end-of-coherent-action); hard trigger at 30k forces a clean cut regardless. A new sidecar worker (`sidecar/src/keeper.ts`, structurally a sibling to `classifier.ts`) makes one `complete()` call against the configured Keeper model with the recent slice + a Rust-canonical system prompt, returning structured JSON `{ claims, compaction_summary }`. Rust's event handler enqueues `PersistCommand` variants on the existing single-consumer pipeline: N × `InsertMemory`, 1 × `CompleteKeeperRun`, 1 × `RecordQuestEvent('compaction_tick')` *when a current quest exists*, and 1 × `RebuildHnsw` at the tail. After the writes settle, Pi's `state.messages` is rewritten — pre-tick raw conversation collapses into a synthesized [user: "previously summarized: \<summary\>" + assistant: "ack"] scaffold; messages since the tick stay as-is. The captain-facing chat UI still reads from the canonical SQLite `messages` table, so the synthesized scaffold only ever exists in Pi's runtime memory for the LLM. If `memory.toml` has no Keeper model configured, the trigger is a silent no-op.

## Relevant files and areas

### Live agent state — token accounting
- `src-tauri/src/agent_state.rs` — `LiveAgentState` already tracks `last_usage`; extend with two fields: `tokens_since_last_compaction: i64` (running sum) and `compaction_pending: bool` (soft-trigger flag set when sum crosses ~25k, consumed by the next breakpoint event). `apply_event` updates both on `MessageEnd { message: { usage } }` paths.
- `src-tauri/src/agent/event_handler.rs` — at `TurnEnd` (and at `ToolExecutionEnd` if we want finer breakpoints), inspect `compaction_pending` and the running sum; if pending and not currently streaming, dispatch a Keeper run. Hard trigger at 30k fires irrespective of pending state.
- Cold-start recovery: on sidecar/app restart, seed the running sum from `messages` rows newer than the last `memory_keeper_runs.completed_at` for that agent (sum their tokens). Avoids losing the count across crashes.

### Wire protocol
- `sidecar/src/protocol.ts` — add a Rust→sidecar `KeeperRunCommand { type: "keeper_run", agentId, runId, slice, config }` and a sidecar→Rust `KeeperResultEvent { type: "keeper_result", agentId, runId, claims?, compactionSummary?, error?, model?, tokensIn?, tokensOut?, latencyMs? }`. The `slice` field carries the textual rendering of recent messages + relevant L3 walk + last L2-shaped summary (string, not structured — L2's typed shape is P4).
- `src-tauri/src/sidecar_protocol.rs` — mirror with `SidecarCommand::KeeperRun { ... }` and `SidecarEvent::KeeperResult { ... }`. Extend `KNOWN_SIDECAR_TAGS` so unknown-fall-through doesn't catch the new variant.

### Sidecar worker
- `sidecar/src/keeper.ts` *(new)* — runner. Same structural shape as `sidecar/src/classifier.ts`: resolves model + auth via `session.modelRegistry`, calls `complete()` once with the system prompt + slice, parses JSON output (with code-fence stripping), never throws. Returns either `{ claims, compactionSummary, model, tokensIn, tokensOut, latencyMs }` or `{ error, model?, latencyMs }`.
- `sidecar/src/runtime-manager.ts` — handle the new `keeper_run` command: pull the managed session for `modelRegistry`/auth, invoke `keeper.run(...)`, emit one `keeper_result` event. Never blocks the executor's in-flight turn — Keeper runs in parallel.

### Rust trigger dispatch
- `src-tauri/src/agent/manager.rs` — new method `dispatch_keeper_run(agent_id) -> Result<run_id>`: inserts a `memory_keeper_runs` row with `outcome='pending'`, `trigger='continuous'`, populated `agent_id`/`model_id`; assembles the slice (see "Slice content" below); resolves the Keeper config from `memory_config::resolved()`; sends a `SidecarCommand::KeeperRun` over the agent's stdin pipe. The trigger from `event_handler.rs` calls into this.
- `src-tauri/src/memory_config.rs` — already loads provider/model. Add `keeper_system_prompt: String` constant in the same module (mirrors `classifier_config.rs`'s `DEFAULT_CLASSIFIER_SYSTEM_PROMPT`) and surface it in `ResolvedMemoryConfig`. Read-only at the UI layer for v1. Add token-threshold fields too: `soft_threshold_tokens`, `hard_threshold_tokens`, both `Option<u32>` with defaults of 25_000 / 30_000.

### Slice content
The Keeper's input is a textual rendering of:
- **Raw stream slice** — the executor's `messages` rows newer than the last `memory_keeper_runs.completed_at` (or all messages for first-ever run), formatted as `[role @ timestamp]: content`. Include tool calls + results inline, paired by id.
- **Relevant L3 slice** — hybrid-search the existing `memories` table for memories related to the slice's recent topics. v1: BM25 top-K=5 from `memories_fts` keyed on the captain's most recent prompt (cheapest signal). Vector retrieval lands properly in MON-101; here we just need a tiny preview so the Keeper knows what's already known and can merge/dedupe in its output.
- **Last L2-shaped summary** — the most recent `memory_keeper_runs.output_summary` for this agent (the prior tick's compaction summary). Empty for first-ever run.

Together: a single `slice: string` field on the `keeper_run` command. ~5-15k tokens typical; well within model context.

### Rust event-handling on keeper_result
- `src-tauri/src/agent/event_handler.rs` — extend with a `SidecarEvent::KeeperResult` arm. Build `PersistCommand`s analogously to `Classification` handling.
- `src-tauri/src/agent/persist.rs` — add new variants:
  - `PersistCommand::InsertMemory { agent_id, payload }` — embeds the content via the shared `MemoryIndex::embed_to_blob` *before* the insert so the row carries an embedding blob; calls `db::insert_memory_internal`. `payload.source_quest_id` set from `agents.current_quest_id` at producer side; `payload.source_session_id` from the agent's current session; `payload.source_events` an array of `messages.id` values for the rows that fed the slice.
  - `PersistCommand::CompleteKeeperRun { run_id, output_summary, tokens_in, tokens_out, outcome }` — calls `db::complete_keeper_run_internal`. On error, `outcome='error'` and `output_summary` carries the message.
  - `PersistCommand::RecordQuestEvent { quest_id, event_type, actor, payload_json }` — generic wrapper around `db::record_quest_event_internal`. For `compaction_tick`, payload includes `{ keeper_run_id, claims_count, summary }`. Also reused by MON-102's `memory_suggestion`. Skip when `quest_id` is None (no current quest).
  - `PersistCommand::RebuildHnsw { agent_id }` — calls `MemoryIndex::rebuild`. Last in the per-tick burst so HNSW state is consistent before the next read.
  - `PersistCommand::ResetCompactionWindow { agent_id, run_id }` — clears `tokens_since_last_compaction` and `compaction_pending` in `LiveAgentState`. Fires the Pi messages rewrite (see next section).
- The persist consumer remains FIFO so a second Keeper run for the same agent can't interleave its writes with the first.

### Pi messages rewrite
- New sidecar command `SidecarCommand::RewriteMessages { agent_id, run_id, summary, tail_anchor }` (or fold into the response path of `keeper_run`). Sidecar replaces `session.agent.state.messages` with a synthesized scaffold:
  - `[user: "[Previous context — Keeper @ <ts>]\n## Summary\n<summary>\n## Relevant memories\n<title — summary>..."]`
  - `[assistant: "Acknowledged. Continuing from this state."]`
  - tail: existing messages newer than `tail_anchor` (id-keyed)
  
  Mechanism mirrors `loadSession` (which already does whole-array replacement). Only the LLM-facing array changes; the SQLite `messages` table is untouched.
- Captain-facing chat UI still reads from the canonical SQLite `messages` table; no DB writes for the synthesized rows.

### Frontend
- `src/lib/toolbox/tools/QuestTimelineTool.svelte` — render `event_type === "compaction_tick"` with a distinct visual treatment in the expanded event log. Show `summary` inline with a small icon; expand to show `claims_count` and `keeper_run_id`. Existing `quest-event-{rootId}` per-root subscription wakes the store when a new event lands; nothing else to wire.
- `src/lib/MemorySettings.svelte` — add UI for soft/hard token thresholds (numeric inputs). Optional for v1; defaults are fine.
- `src/lib/bindings.ts` — regenerated automatically when new Tauri commands or types land.

### Configuration
- `~/.config/monarch/memory.toml` — extends with `soft_threshold_tokens` / `hard_threshold_tokens`. The Keeper system prompt stays in code (`memory_config.rs` constant), exposed read-only through `ResolvedMemoryConfig` for the settings UI to display.

## What needs to change

### 1. Token counter + soft/hard trigger
- Sum `usage.total_tokens` per agent in `LiveAgentState`. Set `compaction_pending = true` at soft threshold. Fire the Keeper at the next `TurnEnd` if pending, or immediately at hard threshold.
- Cold-start recovery: on app/sidecar restart, seed the sum from messages newer than the last successful run.

### 2. Sidecar Keeper worker
- New `keeper.ts` mirrors `classifier.ts` shape. System prompt comes from Rust per-call (canonical, evolves with product).
- Output `{ claims: AtomicClaim[], compactionSummary: string }` or `{ error }`. Never throws.

### 3. Rust trigger dispatch + persist variants
- `dispatch_keeper_run` in `manager.rs`: insert pending run row, ship `keeper_run` command.
- New `PersistCommand` variants for `InsertMemory`, `CompleteKeeperRun`, `RecordQuestEvent`, `RebuildHnsw`, `ResetCompactionWindow`. Pipeline stays FIFO.

### 4. Pi messages rewrite
- After the persist consumer applies the run's writes, fire `RewriteMessages` to the sidecar. Sidecar swaps `state.messages` with the synthesized scaffold + tail. Captain UI is unaffected.

### 5. compaction_tick rendering
- Branch in `QuestTimelineTool.svelte` for the new event kind. Existing subscription wiring suffices.

### 6. Silent no-op when memory disabled
- `dispatch_keeper_run` reads `ResolvedMemoryConfig`. If `enabled == false`, the trigger never fires (the soft/hard thresholds simply accumulate harmlessly).

### 7. Manual verification
- Configure Keeper model in Settings → Memory.
- Start a long conversation (or several rounds of bash output via the executor).
- Watch token counter cross ~25k → next turn-end fires the Keeper → memories appear in the Inspector with provenance.
- Inspect the next request to the LLM (Anthropic request log or sidecar debug output) — should carry the synthesized scaffold, not the full history.

## Open questions

1. **Slice content for first-ever run.** No prior `memory_keeper_runs` row → no anchor for which messages are "new." Recommendation: include all messages for the agent's current session. Worst case for token count if the conversation has run hot for a while, but typical first runs hit at ~30k anyway. Lock at impl time.

2. **Hybrid retrieval preview during the slice.** v1 plan above uses BM25-only top-K=5 from `memories_fts` to give the Keeper a sense of "what's already known." Vector retrieval is MON-101 territory. Is that preview enough for the Keeper to do meaningful merge/dedupe at v1 volumes (probably <50 memories per agent), or do we want a minimal vector path here too? Recommendation: BM25-only is fine for P2 — at low volumes BM25 has high recall on title+summary fields, and the Keeper's merge logic is forgiving (sibling-insert at low cosine).

3. **Keeper system prompt content.** `distillation.md` § "What the Keeper produces per tick" + § "Atomic claims" + § "What NOT to capture" defines the contract; the actual prompt text is locked at impl time. Initial version: explicit JSON schema, atomic-claim definition, "what NOT to capture" exclusions, merge/supersede/insert/sibling thresholds described in plain English (real cosine logic is P3a-calibrated). Calibration follows P3a metrics.

4. **Pi messages rewrite races.** What if the Keeper run completes mid-streaming-turn? `state.messages` is being mutated by Pi's own append path during a turn. Mitigation: defer the rewrite until `agent_end` is observed. Practically: enqueue the rewrite as a `PersistCommand` after the tick's other writes; the persist consumer's FIFO ordering plus the deferred-until-`agent_end` guard prevents the rewrite from landing mid-turn. Verify under load.

5. **Token-counter accuracy with usage.cacheRead/cacheWrite.** Anthropic's usage object splits cached vs uncached tokens. For threshold purposes we want *total context billed* — which includes cache reads. The simplest accurate count is `usage.input + usage.output + usage.cacheRead + usage.cacheWrite`. Confirm field names against pi-ai's `Usage` type at impl time.

6. **What to do if the Keeper run fails (network, bad JSON).** No memories written; the run row marks `outcome='error'`. Should the messages rewrite still fire? Recommendation: no — keep the raw history intact and let the next threshold crossing retry. If retries fail repeatedly, the agent's context grows unbounded; flag a notification (existing `notificationsStore`) at e.g. 50k tokens with no successful tick to surface the failure to the captain.

7. **Coordination with Pi's built-in `compact()`.** Pi may try to compact on its own when context approaches the model's window limit. We're replacing that path for opted-in agents. Need to verify whether disabling Pi's compaction (or letting it run as a fallback when our Keeper is disabled) is the right move. Recommendation: if `ResolvedMemoryConfig.enabled == true`, override Pi's compact to no-op via the extension hook; otherwise let it run. Investigate the hook surface at impl time.
