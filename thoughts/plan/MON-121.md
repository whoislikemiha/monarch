# MON-121 — P6 Slice C: quest report renderer in the quest detail panel

Research plan. Captain-facing read surface for the first-person quest report.

## Summary

P6 Slice A (MON-119) shipped the `quest_reports` storage substrate plus
`db_get_quest_report` / `db_list_quest_reports_for_agent` and the
`quest-report-{quest_id}` event. P6 Slice B (MON-120) shipped the producer —
the executor's `complete_quest(report)` tool, the inbound `quest_report`
event, and the pipeline command that writes the report + closes the quest in
one atomic step.

Slice C is purely frontend. The expanded quest detail panel in
`QuestTimelineTool.svelte` renders the first-person report when it exists:
summary, outcome, decisions, learned, artifacts, open_threads, reflection,
grade. The section is read-only — the report is the shadow's own artifact,
distinct from captain-editable quest fields P5 already owns.

## Relevant files

### Frontend

- `src/lib/toolbox/questStore.svelte.ts` — per-agent cache for quests, events,
  refs, plan items. Slice C adds a `reportsByQuest` cache mirroring the
  refs/events pattern (lazy-loaded on expand, invalidated on live event).
- `src/lib/toolbox/tools/QuestTimelineTool.svelte` — the expanded quest
  detail panel (~lines 1001–1160 in the existing file). The new section
  renders below the refs panel and above the manual-event form.
- `src/lib/bindings.ts` — `dbGetQuestReport` (~244) returns the row inline;
  the named `QuestReportRow` type (~799) carries the same shape and is what
  the store imports.
- `src/lib/api.ts` — `invoke` / `listen` abstractions; new code uses these,
  not direct `@tauri-apps/api` imports.

### Payload shape (Rust + sidecar)

- `sidecar/src/report-tools.ts` (~52–120) — the structured shape the executor
  emits via `complete_quest`. Snake-case keys: `summary`, `outcome`,
  `decisions[{decision, rationale?}]`, `learned[]`,
  `artifacts[{file, role}]`, `open_threads[]`, `reflection`, `grade`.
- `src-tauri/src/sidecar_protocol.rs` `QuestReport` (~258–277) — the Rust
  struct, `Serialize`/`Deserialize` with snake-case field names. Verbatim
  what lands in the DB column.
- `src-tauri/src/agent/persist.rs` `CompleteQuest` apply arm — calls
  `serde_json::to_string(&report)` and stores the result in
  `quest_reports.payload`. So the UI parses the same snake-case shape.

## What needs to change

### 1. questStore — parsed-report cache

- A new `QuestReportView` interface with the snake-case fields, plus the
  row's `distilledByKeeperRunId` and `updatedAt` for context.
- A `parseQuestReport(row)` helper (exported for unit testing) that parses
  `row.payload`, supplies empty defaults for missing fields, and on JSON
  failure returns a degraded view carrying `raw: row.payload` so the renderer
  can branch to a fallback path. Non-array list fields are coerced to `[]`.
- A `reportsByQuest: SvelteMap<string, QuestReportView | null>` field. `null`
  means "loaded, no report exists"; an absent key means "not yet fetched".
- A `loadReport(agentId, questId)` method that invokes `db_get_quest_report`
  and stores either `parseQuestReport(row)` or `null`.
- Lazy load in `toggleExpand` alongside the existing
  events/planItems/refs hydration.
- A per-quest subscription on `quest-report-{questId}` in
  `wireRootSubscriptions`. If the quest is expanded, refetch; otherwise drop
  the cache so the next expand pulls fresh.

### 2. QuestTimelineTool — read-only render

- A `{@const report = questState.reportsByQuest.get(quest.id) ?? null}`
  alongside the existing `events` / `refs` consts at the loop scope.
- A `.report-panel` section placed after the refs panel and before the
  manual-event form, gated by `{#if report}` so an unreported quest shows no
  empty shell.
- A header row showing the section title, an `outcome` chip (color-coded:
  done = positive, abandoned/blocked = negative), and a `grade` chip when set.
- Sub-blocks for `summary` (paragraph), `decisions` (list with optional
  rationale), `learned`, `artifacts` (role + file in mono), `open_threads`,
  and `reflection` (italic paragraph). Empty fields drop their block entirely.
- A `raw` branch renders the unparsed payload in a `<pre>` with a "could not
  parse" notice — the captain at least sees the text.

### 3. Styles

- Reuse the `.refs-panel, .manual-event-form` flex/border idiom; add
  `.report-panel` to that selector. New rules for `.report-outcome`,
  `.outcome-done`, `.outcome-abandoned`, `.outcome-blocked`, `.report-grade`,
  `.report-label`, `.report-list`, `.report-rationale`,
  `.report-artifact-role`, `.report-artifact-file`, `.report-reflection`, and
  `.report-raw`. Use existing CSS vars (`--border-subtle`, `--text-muted`,
  `--text-primary`, `--bg-sidebar`); fall back via `var(--x, default)` for
  variables that may not exist in every theme.

### 4. Tests

`src/lib/toolbox/questStore.test.ts` — Vitest covering `parseQuestReport`:

- well-formed payload round-trips verbatim;
- missing fields receive empty defaults (`""` / `[]`);
- malformed JSON does not throw and yields a view with `raw` set;
- non-array list fields coerce to `[]`;
- row metadata (`distilledByKeeperRunId`, `updatedAt`) flows through.

The renderer itself is not unit-tested (matches the rest of the toolbox tools
— UI behavior is verified manually in `tauri dev`).

## Resolved decisions

- **Read-only.** Report stays read-only. P5 already owns captain-editable
  quest fields (scope / direction / rationale / grade / summary on the quest
  node). The report is the shadow's first-person artifact and should not be
  captain-rewritten in-app.
- **Parsed in the store, not the component.** Parsing lives in the store so
  the component sees a typed `QuestReportView` and the parser is unit-
  testable. Mirrors how `eventsByQuest` / `refsByQuest` are typed.
- **Live update by invalidation, not delta.** The `quest-report-{quest_id}`
  event triggers a refetch when expanded and a cache drop when collapsed —
  same posture as `quest-refs-{quest_id}` in this store. The event payload is
  not consumed directly.
- **Empty fields drop their block.** The renderer hides blocks with no
  content rather than showing a section title above an empty list, so quiet
  reports stay compact.

## Out of scope

- Captain-edit affordances for the report itself (no need — see above).
- Keeper consuming `quest_reports.payload` on quest-close ticks — Slice D.
- A standalone "Reports" listing surface using `db_list_quest_reports_for_agent`
  (the inline panel is sufficient for P6's captain milestone; a dedicated
  listing UI can come later if it earns its own ticket).
