# MON-83 — Quest schema & read-only UI (Slice 2)

Research plan for Slice 2 of the Quest system. Design context: [`plans/quests.md`](../../plans/quests.md).
Linear: https://linear.app/monarch-commander/issue/MON-83

## Summary

Land the Quest data model (two new tables, two FKs on existing tables) and a minimal read-only timeline UI that lets the Monarch manually create a quest + sub-quests and see them rendered. This slice intentionally stops short of automatic decomposition (Slice 3), branch rendering (Slice 6), drift/dispute handling (Slice 4), and EXP (Slice 7). Done means: schema lands without breaking existing persistence, CRUD commands are reachable from both the Tauri host and the WebSocket bridge, and a new Toolbox tool renders a single-lane tree with status/grade/avatar per node plus a detail panel with an event log.

The work slots cleanly into existing conventions: `db.rs` post-launch `ALTER TABLE` migrations, tauri-specta command registration, the `$lib/api` IPC abstraction, and the Toolbox registry. Nothing here requires new infrastructure — only new tables, new commands, and a new Svelte component plus a small `Quest`-focused store. Slice 3 (Architect) is the first caller that will populate `messages.quest_id`; in Slice 2 we add the column, leave it NULL everywhere, and make sure the query surface can filter by it.

## Relevant files and areas

### Backend (Rust)

- **`src-tauri/src/db.rs`** — authoritative schema + async query wrappers.
  - `init_schema` body: base `CREATE TABLE IF NOT EXISTS` blocks live at lines ~123-241; post-launch idempotent `ALTER TABLE` / `CREATE TABLE` migrations live at lines ~243-310. New tables and columns go into the **migrations section**, not the base blocks (CLAUDE.md "Schema evolves via `ALTER TABLE` migrations" is the rule).
  - `save_message_internal` (line ~673) is the single INSERT site for `messages`; any `quest_id` wiring must pass through here.
  - Existing status enums (e.g. on other tables) are encoded as `TEXT` with `CHECK (status IN (...))` — same pattern for the quest status enum.
  - Timestamps are RFC3339 strings via `strftime(...)`, matching sibling columns.

- **`src-tauri/src/agent/persist.rs`** — single-consumer persistence pipeline (MON-37). Bounded `mpsc`, one consumer, FIFO ordering. **Sidecar-originated writes** go through here. **User-initiated writes** (the "New Quest" button, manual status edits) do not — they call DB methods directly from Tauri command handlers. Slice 2 quest writes are all user-initiated; we leave this pipeline alone except that Slice 3+ (and later the Steward) will extend `PersistCommand` with quest-mutation variants.

- **`src-tauri/src/agent/commands.rs`** + **`src-tauri/src/lib.rs`** — Tauri command pattern. Request DTOs are structs (`#[derive(Deserialize, specta::Type)]`) to stay under Specta's 10-arg limit; commands are `async fn`, annotated with `#[tauri::command]` + `#[specta::specta]`, and registered in `lib.rs` via `collect_commands![...]`. `cargo run -- --export-bindings` regenerates `src/lib/bindings.ts`.

- **`src-tauri/src/ws.rs`** — WebSocket bridge. `dispatch_command(state, cmd, args)` has a `match` on the command name; adding a new command means adding one match arm that deserializes `args`, calls the same backend function the Tauri handler calls, and serializes the result. CLAUDE.md: "WebSocket bridge mirrors Tauri commands."

- **`src-tauri/src/agent/event_handler.rs`** — emits `agent-state-{id}`, `agent-event-{id}`, `agent-exit-{id}`. The `emit_event` / `emit_state_event` helpers take arbitrary channel names, so `quest-created-{questId}` / `quest-updated-{questId}` need no central registration. Slice 2's UI is read-on-demand; event emissions can be deferred to later slices if that simplifies scope, but the naming convention should be reserved now.

- **`src-tauri/src/error.rs`** — `MonarchError` is the unified error type returned from Tauri commands. New quest commands follow the same pattern.

### Frontend (Svelte 5)

- **`src/lib/api.ts`** — `invoke<T>(cmd, args)` and `listen<T>(event, handler)` route to Tauri or WebSocket transparently. CLAUDE.md rule: never import `@tauri-apps/api` directly from frontend code. All quest command calls and event subscriptions go through this module.

- **`src/lib/bindings.ts`** — auto-generated by tauri-specta. **Do not edit.** Regenerate after Rust changes.

- **`src/lib/toolbox/registry.ts`** — ordered list of `ToolDefinition` entries. Adding a quest timeline tool = appending one entry (`id: "quest-timeline"`, title, icon SVG, component reference, `hasBackend: true`). Ordering reserved so it lands next to Stats.

- **`src/lib/toolbox/tools/ShadowStatsTool.svelte`** — best existing template for a DB-backed tool: takes `agentContext: ToolProps`, loads on `$effect`, renders with `$state` / `$derived`. Quest timeline tool should mirror this shape.

- **`src/lib/avatar/ShadowAvatar.svelte`** — component used by `AgentRoster` / `AgentPortrait`. Accepts `agentId`, `size`, `avatarType`, `avatarPath`. Re-used inside quest nodes to render the assignee at a smaller size.

- **`src/lib/toolbox/types.ts`** — `ToolProps` + `ToolDefinition` shape.

- **`src/App.svelte`** — top-level layout (roster / agent view / tool panel stack). No changes needed; quest timeline lives inside the existing tool panel.

### Docs

- **`CLAUDE.md`** — "Start Here" table should gain one row for the new quest module once it lands; Rules & Gotchas section already covers post-launch migrations.
- **`ONBOARDING.md`** — section 12 (full file reference) and the data-model walkthrough should gain quest tables. Updating these in the MON-83 PR keeps the docs alive rule honored.

## What needs to change

### 1. Database — two new tables, two FK additions

- Add idempotent migration blocks in `db.rs`'s post-launch section for:
  - `quest_nodes` with all columns listed in the ticket (id PK, `root_id` + `parent_id` self-refs, self-ref FKs for `branched_from_id` and `superseded_by_id`, `assignee_shadow_id` → `agents(id)`, lifecycle timestamps, grade/exec-hint CHECK constraints, status CHECK constraint covering the 9-state enum).
  - `quest_events` with `quest_id` → `quest_nodes(id)`, free-form `event_type`, `actor`, JSON payload, `created_at`.
  - `ALTER TABLE messages ADD COLUMN quest_id TEXT REFERENCES quest_nodes(id);`
  - `ALTER TABLE agents ADD COLUMN current_quest_id TEXT REFERENCES quest_nodes(id);`
- Add indices: `quest_nodes(root_id)`, `quest_nodes(parent_id)`, `quest_nodes(assignee_shadow_id, status)`, `quest_events(quest_id, created_at)`, `messages(quest_id)`. Tree traversal and event-log retrieval are the hot paths.
- Decide encoding for `grade`, `exec_hint`, `status`, `created_by` — all naturally fit `TEXT NOT NULL CHECK (... IN (...))`. `explore_fork_count` stays `INTEGER` nullable (only set when `exec_hint='explore'`).

### 2. Rust — quest module

- New module `src-tauri/src/quest/` containing:
  - `mod.rs` — public facade.
  - `types.rs` — `Quest`, `QuestEvent`, `QuestStatus`, `QuestGrade`, `ExecHint`, `CreatedBy`, `CreateQuestRequest`, `UpdateQuestRequest`, `RecordEventRequest`. All derive `Serialize/Deserialize/specta::Type`. Status/grade/exec enums map 1:1 to the DB CHECK values.
  - `db.rs` — async DB methods on `Database`: `create_quest`, `update_quest`, `get_quest`, `list_quests_for_agent`, `get_quest_tree_for_root` (recursive, assemble parent→children map and return a flattened list ordered by depth + `started_at`), `record_quest_event`, `list_quest_events`. Prefer putting these on `Database` (in `db.rs`) to match existing convention, or pull them into `quest/db.rs` if cleaner — either is fine, decide during implementation.
  - `commands.rs` — Tauri handlers wrapping each DB method. Mirrors `agent/commands.rs` shape.
- Register commands in `lib.rs`'s `collect_commands![...]` list and add matching match arms in `ws.rs::dispatch_command`.
- Regenerate `src/lib/bindings.ts` with `cargo run -- --export-bindings`.

### 3. Frontend — quest timeline tool

- New `src/lib/toolbox/tools/QuestTimelineTool.svelte`:
  - Accepts `{ agentContext }: ToolProps`.
  - On agent change (`$effect`), calls `invoke("list_quests_for_agent", { agentId })` then, for each root, `invoke("get_quest_tree_for_root", { rootId })`.
  - Renders a single vertical lane per root quest. Each node: title, status pill (color from status enum), grade badge (E–S), assignee avatar via `<ShadowAvatar size={28} />`, relative timestamp.
  - Click node → opens inline detail panel (could be a right-slide drawer inside the tool, or a modal — pick one and match existing UI patterns).
  - Detail panel shows: all node metadata, estimated vs actual counters, and the full event log from `list_quest_events`.
  - "New quest" button opens a minimal form: title, optional description, optional parent quest (dropdown of existing quests on this agent), grade, exec hint. Submits via `invoke("create_quest", ...)`.
- New small store at `src/lib/toolbox/questStore.svelte.ts` (runes) keyed by `agentId` → `{ quests: Quest[], events: Map<questId, QuestEvent[]> }`. Keeps UI reactive and survives agent switches (per CLAUDE.md "Toolbox tools stay mounted across agent switches").
- Register in `src/lib/toolbox/registry.ts` after the existing Stats entry (order ~20).

### 4. Event channel reservations (optional for Slice 2)

- If emit sites are easy to slot in now, have `create_quest` / `update_quest` / `record_quest_event` emit `quest-created-{questId}` / `quest-updated-{questId}` / `quest-event-{questId}` via the existing `emit_event` helper. This lets the frontend subscribe once and avoid re-polling. If this expands scope, defer to Slice 3 — the tool can re-query on action.

- Update ONBOARDING.md data model + file reference sections.

## Resolved decisions

1. **Manual quest creation UX** — lives **inside the quest timeline toolbox tool**. Keeps the tool in the toolbox registry (per user direction: "keep it in toolbox for now").
2. **Quest detail view** — opens in a **separate expandable window** when a node is clicked. Implementation: a dedicated overlay/drawer component rendered at the `App.svelte` level (so it can grow beyond the tool panel's width), mounted conditionally from a small shared `questDetailStore` that the toolbox tool writes to on click. The toolbox stays as the entry point and timeline; the expanded view is the detail surface.
3. **`list_quests_for_agent` semantics** — **assignee-only** (`WHERE assignee_shadow_id = ?`). `agents.current_quest_id` is a pointer into the tree, not a list filter.
4. **Read-only + event log** — resolved by **auto-seeding a creation event** (`event_type='status_change'`, `payload={from: null, to: 'pending'}`, `actor='monarch'`) inside `create_quest`. Status editing UI is deferred; the log still has content for the success criterion.
5. **Event channels** — **emit in Slice 2.** `create_quest` → `quest-created-{questId}`; `update_quest` → `quest-updated-{questId}`; `record_quest_event` → `quest-event-{questId}`. One line per write, makes Slice 3 integration free.
6. **Create-form defaults** — `grade='C'`, `exec_hint='in_context'`, `status='pending'`, `created_by='monarch'`. All user-overridable except `created_by`.
7. **`agents.current_quest_id`** — add the column now, leave NULL. Slice 3 populates it.
8. **Quest IDs** — **UUID v4 strings** (matches `agents.id` / `sessions.id`).
