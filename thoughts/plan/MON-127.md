# MON-127 — Proper chat history: real multi-session support, session browser, working new-session

Linear: https://linear.app/monarch-commander/issue/MON-127/proper-chat-history-real-multi-session-support-session-browser-and

## 1. Summary

Each shadow today effectively has one endless conversation. All the session machinery exists — `sessions.parent_session_id` ancestry, `new_agent_session` / `switch_agent_session` commands, `get_messages_with_ancestry` as the canonical history loader — but the frontend wires it so that "New session" creates a session row whose `parent_session_id` points at the previous session (`agentStore.newConversation`, `src/lib/stores/agentStore.svelte.ts:527`). Because both display rebuild (`rebuild_agent_state_from_session`) and sidecar context replay (`load_session_context`) walk the full ancestry chain, the "new" session inherits the entire prior conversation: from the user's point of view nothing happened. The only history surface is the legacy `HistoryPanel` modal, which lists sessions but always previews/continues the full chain. The goal is to make sessions real: "New session" starts a genuinely fresh conversation, a design-system session-history surface lets the user browse past sessions and reopen/continue any of them, and the semantics of fresh / continue / ancestry-linked sessions are made coherent and documented. This is the foundation the workspace's scoped-chat seam (MON-124) assumes.

## 3. What needs to change

1. **Fix new-session semantics (backend-adjacent, mostly frontend wiring).** `newConversation` must create a session with **no** `parent_session_id` (fresh context), while `spawnStoppedAgent`/restore keep chaining (intentional continuation). Decide and encode the three cases explicitly: *fresh* (no parent), *continue-in-place* (reuse existing row via `switch_agent_session`), *continuation-with-ancestry* (new row + parent, used by respawn/restore). The store methods should map one-to-one onto these.

2. **Make switching actually reset the pane.** On fresh-session start, the live display state and sidecar context must be cleared, not replayed: verify the `NewSession` sidecar command + `viewKey` remount path leaves no stale `LiveAgentState` (the in-memory cache in Rust keyed by agent id is the risk — `get_agent_state` seeding may resurrect the old conversation). Likely needs an explicit state-reset on the Rust side when the active session changes.

3. **Session history surface (new, design-system, toolbox tool).** Replace `HistoryPanel` with a toolbox tool that lists an agent's sessions (`db_get_sessions`) with date, message count, token/cost, and a title (`sessions.title`, falling back to a derived first-user-message preview — may warrant a small query addition in `db/sessions.rs` rather than fetching full ancestry per row). Selecting a session shows *that session's* messages read-only. A "continue" action makes it the active session via the existing `switchSession` path.

4. **Read-only history rendering.** Rendering a past conversation without binding it to the live stream needs a display path that goes `db_get_messages(_with_ancestry)` → display items on the frontend, independent of `LiveAgentState`. Decide whether to reuse Rust's `display_items_from_messages` via a new query command (consistent rendering, one converter) or do a lightweight frontend renderer (less plumbing, risk of drift). Leaning toward exposing the Rust converter.

5. **Session identity/metadata polish.** Sessions have no human-friendly handle. At minimum derive a title from the first user message at display time; optionally add a nullable `sessions.title` column via an `ALTER TABLE` migration block (schema-evolution rule) so future features (scoped chats) can name sessions. Decision below.

6. **Remove/retire `HistoryPanel`** once the new surface covers list/preview/continue, and update `ShadowHeader`'s actions menu to point at the new surface.

7. **Docs.** ONBOARDING.md gets the three-case session semantics table and the new surface; CLAUDE.md gotchas updated if the "new session ≠ ancestry child" rule is worth pinning.

## 4. Decisions (open questions resolved 2026-06-12)

1. **Per-session display when browsing.** The history surface shows *just that session's* messages (`db_get_messages`), not the full ancestry chain. An optional collapsed "N earlier messages from parent sessions" affordance may be added, but per-session is the canonical view.
2. **Continue semantics + timeline.** Continue keeps the current behavior: reuse the existing session row via `switch_agent_session`. The deciding factor: the execution timeline is keyed purely by `agentId` and paged from `objective_events` (`src/lib/workspace/timelineStore.svelte.ts`), so it is session-independent and survives any switch/new-session untouched — forking sessions would buy nothing there. Implementation must verify the only session-coupled live state (NOW strip / current action from `LiveAgentState`) resets correctly on fresh sessions and rehydrates on continue.
3. **`sessions.title`.** Add the nullable column now via an `ALTER TABLE` migration block; derive a fallback title from the first user message at display time when NULL.
4. **History surface lives in the toolbox.** Build it as a toolbox tool (`src/lib/toolbox/tools/SessionHistoryTool.svelte`, registered in `registry.ts`), keyed by `agentContext.agentId` since toolbox tools stay mounted across agent switches.
5. **MON-124 is merged** (PR #106, rebase-merged 2026-06-12). This branch is off post-merge master and already contains the timeline work — no coordination concern.

## 5. Out of scope

- Paged/infinite-scroll loading of messages within one conversation (separate performance issue).
- Cross-agent full-text search over history.
- Scoped timeline chats themselves — this issue only builds the session foundation they require.
- Branching/forking UI beyond linear continue semantics.
