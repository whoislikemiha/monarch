# MON-110 — P4b: Execution plans (intended route)

## Summary

P4 made executor activity legible at the action level — the timeline reads as a real execution narrative, and the Agent View `Now:` strip surfaces the live action. P4b adds the third layer in `substrate.md` § L2 "Three layers of intention": a durable, captain-visible, provisional **execution plan** — what the shadow currently intends to do next.

The plan is per-quest, ordered, and lifecycle-stamped (pending / active / completed / skipped / blocked). The executor declares it via narration tools that mirror MON-108's pattern, the persistence pipeline owns IDs and ordering, L2 working memory carries pointers (`active_plan_item_id`, `next_plan_item_ids`) rather than item rows, and coherent actions auto-link to the plan item that was active when they ran. The captain reads the plan in a lightweight panel and can edit/reorder manually. Quests without a plan keep working exactly as in P4 — plan is opt-in.

P4b is filed as parent **MON-110** with three slices:

- **Slice A — MON-111** (persistence): schema, lifecycle handlers, action-to-plan-item stamping, L2 rebuild fallback.
- **Slice B — MON-112** (sidecar): narration tools + executor prompt block.
- **Slice C — MON-113** (frontend): plan panel, timeline plan-item highlighting, `Now:` strip extension.

## What needs to change

### Slice A — substrate (MON-111)

**Schema migrations** (idempotent, end of `init_schema`):
1. `CREATE TABLE IF NOT EXISTS quest_plan_items (id, quest_id, parent_id NULL, title, status, order_index, created_by, rationale NULL, created_at, updated_at, completed_at NULL)` plus indexes on `(quest_id, order_index)` and `(quest_id, status)`. `created_by` CHECK includes `'executor'` from the start (the existing `quest_nodes.created_by` enum doesn't carry it; new column means clean slate).
2. `ALTER TABLE quest_events ADD COLUMN plan_item_id TEXT REFERENCES quest_plan_items(id) ON DELETE SET NULL` plus index. Must run after the table is created.

**L2 shape** — extend `WorkingMemoryPayload` with `active_plan_item_id: Option<String>` and `next_plan_item_ids: Vec<String>` (cap to 3). Bump `schema_version` to 2; default the new fields to make v1 rows deserialize cleanly. Document the v2 shape next to v0/v1 in the comments.

**Event taxonomy** — add `plan_created`, `plan_item_started`, `plan_item_completed`, `plan_item_skipped`, `plan_item_blocked`, `plan_changed` as new `quest_events.event_type` strings. Author is `executor` for all P4b emissions. `payload_schema_version` stays at 1 (it's payload-internal, not a global discriminator).

**`PersistCommand` variants** — at minimum:
- `PlanCreateOrReplace { agent_id, quest_id, items, rationale? }` — bulk upsert + emit `plan_created` (or `plan_changed` if pre-existing).
- `PlanItemTransition { agent_id, quest_id, item_id, new_status, payload }` — handles started/completed/skipped/blocked, emits the lifecycle event, mutates L2 `active_plan_item_id` and `next_plan_item_ids` atomically.
- `PlanUpdate { agent_id, quest_id, diff }` — reorder/insert/edit/remove + emit `plan_changed`.

**Action-to-plan stamping** — inside `record_action_transition_internal`, after loading L2 in the tx, pass `active_plan_item_id` to the `coherent_action` INSERT. Stamping `executor_decision` and `tool_call` is optional and called out in open questions.

**L2 rebuild fallback** — extend MON-107's rebuild plumbing so a missing/invalid `agent_working_memory` row reconstructs `active_plan_item_id` and `next_plan_item_ids` from the most recent `plan_item_started` / `plan_item_completed` / etc. events on the active quest, joined against `quest_plan_items.status`.

**Tauri commands** — `db_create_plan(payload)`, `db_update_plan(payload)`, `db_list_plan_items(quest_id)`, `db_get_plan_item(item_id)`, plus per-item lifecycle commands. Each `#[tauri::command] #[specta::specta]`. Register in `lib.rs`.

**Tests** — in the `#[cfg(test)] mod tests` block at the bottom of `db.rs`, add: `plan_create_inserts_ordered_items`, `plan_item_started_sets_active_plan_item_id_in_l2`, `plan_item_completed_advances_l2_pointers`, `plan_item_skipped_marks_skipped`, `plan_update_reorder_persists`, `action_transition_stamps_plan_item_id_when_l2_has_active`, `action_transition_skips_stamp_when_no_active_item`, `l2_rebuild_includes_plan_slice`.

### Slice B — sidecar narration (MON-112)

**New file `sidecar/src/plan-tools.ts`** — a `createPlanTools(agentId, emit)` factory mirroring `narration-tools.ts`. Six tools: `set_plan(items, rationale?)`, `update_plan(diff)`, `start_plan_item(item_ref)`, `complete_plan_item(outcome?)`, `skip_plan_item(reason?)`, `block_plan_item(reason)`. Each tool's `execute` body emits an `InnerEvent` whose tag matches the new Rust variants, returns a minimal text acknowledgement (e.g. resolved item id + index), never echoes plan JSON back into context.

**Wire in `runtime-manager.ts`** — spread `createPlanTools(...)` into `customTools` at line 383 alongside narration tools.

**Hide from tool-call rendering** — extend `is_narration_tool` (`persist.rs` line 844) `matches!` with the six new tool names so plan tool calls don't double-persist as `tool_call` events.

**Prompt block in `shadow-oath.ts`** — append `## Execution Plan` after `## Action Narration`. Cover:
- Plan items are intended route, not history.
- Granularity: a plan item is roughly one or a few coherent actions — coarser than tool calls, finer than the quest goal.
- When to declare vs update: declare early when non-trivial; edit when reality diverges; never silently abandon — mark skipped/blocked with a reason.
- Title style: short, action-shaped. Rationale: optional, short.
- One worked end-to-end example: `set_plan` → `start_plan_item` → coherent actions under it → `complete_plan_item` → `start_plan_item` next → `update_plan` when an unexpected step appears → `skip_plan_item` → `complete_plan_item`.

Update the inline tool-name list at lines 112–114 to include the six new tools.

**Graceful degradation** — if no current quest exists when a plan tool fires, reuse MON-107's repair path (gentle auto-create). Document this in the prompt as well so the executor knows it's safe to call plan tools at any point.

### Slice C — frontend (MON-113)

**Bindings** — regenerate after Slice A.

**Quest store** — add `planItemsByQuest: SvelteMap<string, PlanItemRow[]>` and a `loadPlanItems(agentId, questId)` method to `AgentQuestState`. Extend the `quest-event-{questId}` listener to invalidate `planItemsByQuest.delete(questId)` when a `plan_*` event arrives.

**`PlanPanelTool.svelte`** — a new toolbox tool registered in `src/lib/toolbox/registry.ts`, sibling to `QuestTimelineTool`. Renders the active quest's plan as a compact ordered list with status pills (pending / active / completed / skipped / blocked), highlights the active item, surfaces the next 1–3 upcoming. Manual affordances: create item, edit title, edit rationale, reorder (drag or up/down), set status, delete. All wired to Slice A's commands. Empty state when the quest has no plan.

**`QuestTimelineTool` updates**:
- Per-kind renderers for `plan_created` / `plan_item_started` / etc. — compact non-action rows distinct from action rows.
- When a `coherent_action` row carries `plan_item_id`, render a small chip with the resolved plan item title (from `questState.planItemsByQuest`).
- Optional: collapsible plan-item header that groups consecutive actions sharing a `plan_item_id`. Decide at build time — costs vs benefit.

**`Now:` strip in `AgentView.svelte`** — when L2 has `activePlanItemId`, render the resolved title beside `currentAction.intent`. Click jumps to / scrolls / highlights the plan panel.

**Compatibility** — quests without a plan render exactly as today (no chips, no header, plan panel shows empty state). Plan tool calls do not appear as `tool_call` rows (Slice B handles this via `is_narration_tool`).

## Open questions

1. **Single `set_plan` tool vs `set_plan` + `update_plan` separately.** Roadmap names both. `set_plan` implies full replacement (bulk upsert), `update_plan` implies partial mutation. Two tools keep the executor prompt unambiguous; one combined tool is simpler. Recommendation: keep both. Decide at MON-112 ticket open.

2. **Where the plan panel lives.** Two options: (a) embed inside the expanded quest row in `QuestTimelineTool`; (b) new sibling `PlanPanelTool` registered in the toolbox. Recommendation: (b) — the panel needs agent-keyed state that mirrors the quest store, and the toolbox already keeps tools mounted across agent switches. Decide at MON-113 ticket open.

3. **Should `executor_decision` and `tool_call` events also carry `plan_item_id`?** Stamping only `coherent_action` is enough to answer "what plan item was active for this action?" via the parent action. Stamping all child events makes raw queries simpler but is redundant. Recommendation: stamp only `coherent_action` in P4b; revisit if reporting needs it later.

4. **Plan item completion auto-advance.** When `complete_plan_item` fires, should the next pending item become active automatically, or wait for an explicit `start_plan_item`? Recommendation: explicit start. Auto-advance hides intent and makes "in between items" hard to represent. The prompt should encourage explicit transitions.

5. **`next_plan_item_ids` cap.** Roadmap says small ordered list. Cap at 3 by default; document the choice. The Agent View strip surfaces "Now / Next", not the whole plan.

6. **L2 rebuild fallback scope.** Roadmap notes MON-107 deferred a full L2 rebuild to a follow-up; P4b's rebuild only needs to populate the plan slice. Confirm at MON-111 ticket open whether to land plan rebuild standalone or together with the deferred general rebuild work.

7. **`quest_events.plan_item_id` ON DELETE behavior.** `SET NULL` keeps event history when a plan item is deleted. Alternative: forbid deleting plan items that have linked events (require archive instead). Recommendation: `SET NULL` for V0; archival semantics are P12 territory.

8. **Plan panel placement on screen.** Above timeline? Side panel? Inline within an "active quest" header? Decide at MON-113 ticket open after sketching.
