# MON-129 — Agent-authored objective substrate: planning + navigation tools (Arc I foundation)

> Research plan. Provenance: grew out of the MON-128 two-organ (chat-shadow + executor) spike, left experimental. The design conversation behind this plan concluded that the two-sessions-per-agent split and multi-agent orchestration solve the same problem (talk-while-working concurrency), so we collapse back to **one session per agent** and invest in the objective substrate instead. This is the Arc I single-shadow foundation everything later (orchestration, worktrees, self-review, story-view) layers onto.

## 1. Summary

The objective tree is already the canonical work substrate in the schema (`objective_nodes` + `objective_plan_items` / `objective_reports` / `objective_refs` / `objective_events`, all with Rust CRUD and persist appliers), but **agents can only operate inside an objective something else made for them**. Objectives are minted by the `auto_create_current_objective_internal` heuristic (one per "meaningful" turn) or by the UI; the agent's existing Pi tools (`set_plan`, `start/complete/skip/block_plan_item`, `complete_objective`, narration) only fill and close a pre-made box. They cannot author the tree's structure or choose what they're working on.

This issue makes the tree **fully agent-authored and agent-navigable** for a single agent in a single Pi session: the agent creates and decomposes objectives in conversation with the captain, activates the one it's working on (driving where narration/tool events land), navigates the tree cheaply (a lightweight snapshot it can drill into on demand), and runs its own plan → work → report loop. The `auto_create` heuristic is removed; `ensure_scratch_objective` stays as the floor so unscoped/trivial work is still captured, not dropped. Most of the work is thin Pi tools over existing Rust plus one real Rust refactor (lifting the "current objective" setter out of the heuristic) — the storage is already there ("schema ahead of behavior").

## 3. What needs to change (conceptual)

**A. Authoring tools (writes).** Add Pi tools — `create_objective` (title, description?, parent?, direction?), `decompose`/`add_subobjective` (create children under a parent), and `set_objective_direction` / `set_scope` (with rationale) — each a thin wrapper emitting an event consumed by a new persist applier over `create_objective_internal` / node updates. Resolve the campaign root for placement the way the existing capture path does (`db_get_campaign_root_for_agent`; project-less agents fall back to the per-agent scratch objective).

**B. Activation (the load-bearing refactor).** Extract the `current_objective_id` update out of `auto_create_current_objective_internal` into a standalone `set_agent_current_objective_internal`, and expose it to the agent as an `activate_objective(id)` tool (and/or auto-activate on `create_objective`). Because `current_objective_id` is durable on the `agents` row, activation persists across turns — the agent only authors/activates when starting genuinely new work, not every turn. Then remove `auto_create_current_objective_internal` at both call sites, keeping `ensure_scratch_objective_internal` as the `None =>` floor so narration/tool events with no active objective still land on scratch.

**C. Navigation (reads, progressive disclosure).** Add `get_tree(scope?)` — a cheap projection over `objective_nodes` alone (id, parent_id, title, status, kind, grade, summary), default-scoped to the current branch + non-terminal statuses + recent, paginated — and `get_objective(id)` — the drill-down joining plan items, recent events, report, refs, and the node's description/direction/rationale. Both go through the memory-search-style request/response bridge so the tool result carries Rust data back. This is the honest replacement for MON-128's fixed, lossy `recall_actions` dump: the agent pulls the depth it needs.

**D. Prompt loop.** Update `shadow-oath.ts`: for non-trivial work, plan in conversation → `create_objective`/`decompose` → `activate` → work, ticking plan items via the existing tools → `complete_objective` with a report. Trivial turns stay on scratch with no ceremony. Objectives are developed in conversation, never auto-guessed; one task spawning from another is a `parent_id` link, not a new ticket.

**E. Wiring + bindings.** Register the new tools in `runtime-manager.ts`; add any new Tauri commands (if UI needs to read the same projections) to `lib.rs` + `websocket/dispatch.rs` and regenerate `bindings.ts`. Keep `cargo test` and `svelte-check` green; add tests for the activation extraction and the scratch-floor fallback (the behavior most at risk of regression).

## 4. Decisions (resolved 2026-06-14)

1. **Orientation: header + pull.** A minimal one-line "current objective" header is auto-injected into the prompt every turn (cheap, always-oriented); breadth and depth come from `get_tree` / `get_objective` pulled on demand. Not everything is tool-pulled — the header guarantees the agent always knows where it is.
2. **Granularity: bias hard against over-decomposition.** Default to plan items within a single objective; create a sub-objective only for a genuinely independent, separately-completable-and-reportable chunk. The prompt actively discourages deep trees — most work is one objective + a flat plan. (Objectives are `kind='objective'` tree nodes; plan items are the flat route within a node.)
3. **`activate` is both.** `create_objective` auto-activates the new node, and a standalone `activate_objective(id)` exists for re-focusing onto an existing node. `current_objective_id` is durable on the `agents` row, so focus persists across turns — the agent only authors/activates when starting genuinely new work.
4. **Status: full lifecycle available now.** Do not gate the agent to an artificial subset — the existing `objective_nodes` status set is settable. `complete_objective` lands `done` for self-completed work (there is no separate reviewer yet). `claimed_done` / `verified` / `disputed` stay in the schema and are reserved for the later self-review arc; the prompt guides the solo agent through the natural `pending → in_progress → done/abandoned` path (+ `superseded` on re-scope). [Interpreting "do it now" as: expose the full lifecycle rather than ship a subset we'd later have to widen.]
5. **`created_by = 'architect'` for agent self-authored objectives.** Semantically correct in the self-architecting model (the shadow plans for itself) and needs no schema change — the CHECK already allows `architect`. If a dedicated marker is wanted later, extend the CHECK via the ALTER-TABLE migration convention. (`objective_plan_items.created_by` already allows `executor`.) "Make whatever changes necessary" → no migration needed for step one.
6. **`get_tree` default scope (confirmed).** Current branch (ancestors + descendants of `current_objective_id`) + other non-terminal nodes + recently-touched, newest-first, paginated; `idx_objective_nodes_assignee_status` backs the status filter. Anything outside the default scope is reachable via `get_objective`.

### Impl-time verification (not a blocker)
- After auto-create is removed, confirm nothing downstream assumes an objective exists per turn: the MON-82 classifier (`classification_id` FK backfill on `message_end`), the Keeper trigger, and `agent_stats` / `agent_tool_usage` must all tolerate "no current objective → scratch."

## 5. Out of scope

- Orchestration / dispatch to other shadows (`assignee_shadow_id` stays effectively single-agent here).
- Worktree-per-objective parallelism (`worktree_path` / `branch_name` / `base_branch` columns untouched).
- The self-review (plan → execute → review → correct) loop, and the `claimed_done → verified/disputed` review states.
- The objective↔branch↔diff "story view" for review.
- Resurrecting or building on the MON-128 chat-shadow / two-session split (salvage only the pause gate + concurrency spike learnings, separately).
