# MON-102 — P2: Executor `suggest_memory` tool (Keeper input firewall)

> **Sibling slices.** Split out of [MON-100](https://linear.app/monarch-commander/issue/MON-100) (Slice B — Keeper write path) so the SDK-shape risk around pi-coding-agent tool registration doesn't gate the headline "memory forms at quest-close" result. MON-99 (substrate, shipped) provides the schema; MON-100 will eventually consume the suggestions; MON-101 (read path) is unrelated. This ticket is independently testable: the suggestion lands as a `quest_events` row regardless of whether MON-100 has shipped — the Keeper just isn't reading them yet.

## Summary

Add a `suggest_memory(title, summary, content)` tool to the executor's Pi session. When the executor calls it, the sidecar emits a typed `memory_suggestion` inner event; Rust's event handler routes it through the existing single-consumer persistence pipeline to `record_quest_event_internal`, producing a `quest_events` row with `event_type='memory_suggestion'`, `actor=agent_id`, `quest_id=agents.current_quest_id`, and `payload_json={ title, summary, content }`. The QuestTimelineTool renders the new event kind with a distinct treatment so the captain can see what the executor flagged. Critically: there is no path from this tool to the `memories` table — the executor *suggests*, the Keeper (when it lands in MON-100) *decides*. The memory-poisoning firewall is enforced by absence of code, verified by a one-line test or grep in the impl notes. If `agents.current_quest_id` is NULL, the tool call is a silent no-op (logged to stderr but not persisted) so a curious-but-quest-less shadow can't pollute `quest_events` with orphan rows.

## Relevant files and areas

### Pi tool registration (the unknown-shape part)
- `sidecar/src/runtime-manager.ts` — `createSession` already calls `session.bindExtensions({ uiContext, commandContextActions, onError })` with `noExtensions: true` on the resource loader. That disables agent-local discovery but should not disable Monarch-supplied extensions registered explicitly. The likely path: pass an additional Monarch-internal extension (one that contributes a `ToolDefinition` for `suggest_memory`) through `bindExtensions` or the `createAgentSession({ extensions })` argument, depending on what the actual SDK shape supports in pi-coding-agent ≥ 0.70.2.
- `node_modules/@mariozechner/pi-coding-agent/dist/core/extensions/index.d.ts` — exports `Extension`, `ExtensionFactory`, `ToolDefinition`, `RegisteredTool`, `ToolCallEvent`. The tool-call lifecycle should mirror the existing first-party tools (`createReadToolDefinition`, `createBashToolDefinition`, etc.) — the patterns are visible in pi-coding-agent's `dist/core/tools/index.d.ts`.
- *Impl-time check:* a small spike. Before writing the protocol, prove the tool registers and is callable in an `npm run tauri dev` session (e.g. log the `ToolCallEvent` in `runtime-manager.ts`'s listener and ask the executor to call it). If the registration mechanism is awkward or missing, fall back path is a session-level handler that watches for a magic prefix in the executor's text output — ugly but unblocks; flag for replacement.

### Wire protocol
- `sidecar/src/protocol.ts` — no new top-level `SidecarCommand` (the tool is invoked by the executor in-process, not by Rust). The new piece is a sidecar-side inner event: `MemorySuggestionEvent` carrying `title`, `summary`, `content`. It rides the existing `AgentEventEnvelope` (the `{ type: "event", agentId, event }` wrapper).
- `src-tauri/src/sidecar_protocol.rs` — add an `InnerEvent::MemorySuggestion { title, summary, content }` variant. Extend `KNOWN_INNER_TAGS` with `"memory_suggestion"`. Extend `KnownInnerEvent` so the strict decode pass succeeds; the `From` conversion to `InnerEvent` mirrors classifier-style fields. `apply_event` returns `ApplyOutcome::NoOp` — this is a side-channel event, not part of the live agent display state.

### Rust persistence
- `src-tauri/src/agent/persist.rs` — extend the existing pipeline. `build_persist_commands` already produces `LogEvent` for every inner event (good — the suggestion is logged automatically). Additionally, when the inner event is `MemorySuggestion`, push a `PersistCommand::RecordQuestEvent { quest_id, event_type: "memory_suggestion", actor: agent_id, payload_json }`. The `quest_id` resolves at the producer side from `agents.current_quest_id` — the same agent-row read other producers use; if `current_quest_id` is NULL the command is dropped before it reaches the consumer (silent no-op).
- The `PersistCommand::RecordQuestEvent` variant is shared with MON-100's `compaction_tick` writer — whichever ticket lands first defines it. Plan accordingly: if MON-100 has not landed when this slice is implemented, this slice introduces the variant; if MON-100 has landed, this slice reuses it.
- `src-tauri/src/agent/event_handler.rs` — no new SidecarEvent envelope; the `Event` arm already routes inner events through `build_persist_commands`. The new `InnerEvent::MemorySuggestion` flows through unchanged once the protocol additions land.

### Frontend
- `src/lib/toolbox/tools/QuestTimelineTool.svelte` — render `event_type === "memory_suggestion"` with a distinct visual treatment in the expanded event-log panel. Show `title` and `summary` inline; `content` opens on hover or expand. Same render pattern MON-100 uses for `compaction_tick`.
- `src/lib/toolbox/questStore.svelte.ts` — no changes; the existing `quest-event-{rootId}` subscription wakes the store when a new event lands, and `db_list_quest_events` returns the new row unchanged.
- `src/lib/bindings.ts` — no Tauri command additions in this slice means no regeneration is required, *unless* the impl decides to also expose a debug-only invoke for hand-testing without the executor. Optional.

## Open questions

1. **Pi tool registration mechanism (spike).** Open Q #2 from MON-100's plan, peeled into this ticket. Three sub-cases: (a) `bindExtensions` accepts a Monarch-supplied extension factory cleanly — most likely; (b) `createAgentSession({ extensions: [...] })` is the right place — also plausible; (c) neither does the right thing and we need a different mechanism (e.g. a `SessionStartEvent` hook adds the tool). Resolved at impl time via a 30-min spike before any other code lands.

2. **Tool input shape.** `suggest_memory(title: string, summary: string, content: string)` is the obvious shape, but should `kind` (claim / decision / observation) and `file_refs` (array of paths) be first-class arguments too? Recommendation: ship with `(title, summary, content)` only for v1. The Keeper can infer `kind` and extract file refs from the claim text. Adding fields later is back-compat; subtracting them isn't.

3. **No-current-quest behaviour.** Silent no-op vs error returned to the executor. Recommendation: silent no-op (logged to stderr) — the executor shouldn't have to know about quest state to decide whether to flag a memory. If we return an error, the executor's tool-result loop sees a failure for what was a perfectly reasonable call. Alternative: route to a special "uncategorized" quest, but that adds product surface for negligible benefit.

4. **Tool output / acknowledgement.** Should the tool return the recorded event id? Or just `{ ok: true }`? Recommendation: `{ ok: true, eventId? }` — the event id is cheap to surface and could be useful later (e.g. a future "Captain rejects this suggestion" flow that needs to reference it). If MON-100 hasn't landed yet, `eventId` is still meaningful — `quest_events` rows exist independently.

5. **Rate limiting / abuse.** Could a misbehaving executor call `suggest_memory` 100 times in a turn? Yes. Recommendation: don't add rate limiting in this slice — captain-set permission gates / pending-action mediation are P8 territory. If we observe abuse during dogfooding, revisit.

6. **Suggestion lifetime when no quest is active later.** A suggestion on quest A persists in `quest_events` even if quest A is abandoned. Is that fine? Yes — `quest_events.quest_id` has `ON DELETE CASCADE`, so deleting the quest cleans up. Abandoned quests stay in the DB by default, so suggestions remain alongside.
