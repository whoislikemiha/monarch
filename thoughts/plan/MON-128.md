# MON-128 — P3: Two-organ shadow (chat-shadow + executor via two Pi sessions per agent)

> Research plan. Design sources: `thoughts/design/shadow-cognition/attention.md` (§ captain experience, § two surfaces, § thread types, § tool taxonomy by thread), `flows.md` (§ chat-shadow per-turn loop, § coordination, § conversation entry conditions), roadmap-v2 § P3. Read those before implementing — the tool lists, event kinds, and pause semantics below are lifted from them.

## 1. Summary

P3 splits a working shadow into two concurrent Pi sessions expressing one identity: an **executor** (full toolset, acts on the world, narrates the timeline) and a **chat-shadow** (read/direct/control only — answers the captain from L2 + the objective event log, and can pause/resume/stop the executor). Both sessions share the substrate (L1 identity via shadow-oath, L2 `agent_working_memory`, L3 memories, objective events); coherence comes from the substrate, not a shared context window.

Two findings reshape the expected scope:

- **The Pi-concurrency risk looks smaller than feared.** Pi SDK has no module-level singletons; `AgentSession` and `SessionManager` are instance-scoped; an upstream concurrent-session test suite exists (`pi/packages/coding-agent/test/agent-session-concurrent.test.ts`); per-session `allowedToolNames`/`excludedToolNames` and `customTools` already support a differently-armed second session. The sidecar's 1-session-per-agent is a keying convention (`Map<agentId>`), not an architectural limit. A short spike still goes first, but it's confirmation, not invention.
- **The dual-surface UI already exists (MON-124).** `TimelinePane` is mounted by default in `SoloWorkspace` as a sibling tile to chat; chat is de-tooled (`ToolActivityChip` links to timeline rows); scoped chats spawn from action cards. P3's frontend work is *re-pointing chat at the chat-shadow session* and splitting streaming sources — not building surfaces.

The bulk of the work is therefore in **Rust**: every layer of `src-tauri/src/agent/` assumes one session per agent (session_map, live state, event dispatch, persistence, keeper, kill). That's the real lift.

## 3. What needs to change

Proposed slices (each independently testable, per the phase rule):

**Slice A — Pi-concurrency spike (timeboxed; goes first).** In the sidecar, spawn two `AgentSession` instances for one agent (same cwd, distinct `SessionManager.inMemory`, distinct tool sets), prompt both concurrently, and verify: event interleaving on stdout is correctly per-session-tagged, no shared-state bleed (extensions, resource loader, model registry), abort on one doesn't disturb the other. Output is a go/no-go note + any constraints discovered (e.g. memory footprint, event ordering). Roadmap-v2 names this the one real technical risk; everything later rides on it.

**Slice B — Session roles in the substrate.** Persist the organ: `sessions.role` (`executor`/`chat`) via ALTER TABLE (decision 3). Sidecar protocol grows a role discriminator on `create_session`/`prompt`/`abort`/`destroy_session`; runtime-manager keys sessions by `(agentId, role)` and tags emitted events with the role. Rust `session_map` becomes role-aware. Migration note: every existing session is `executor`.

**Slice C — Rust plumbing for the second session.** The single-session assumptions list, worked through: event_handler resolves session by (agent, role) from the event tag; persist pipeline writes chat turns to the chat session's rows; keeper slice and classifier gate to executor-session content only; `kill()` tears down both organs; `new_session`/`switch_session` (MON-127 semantics) operate on the executor session and leave the chat organ alone. Live state: `agent-state-{id}` stays the executor stream, byte-identical to today; chat gets its own `agent-chat-state-{id}` channel (decision 4). The chat session is spawned lazily on first chat input, survives executor restarts and new executor sessions, and dies with the agent (decision 7). The handoff injection path (decision 1) — verbatim fenced slice, watermark, `dispatched_to_executor` event — lands here on the Rust side.

**Slice D — Chat-shadow session: tools + prompt.** A read/direct/control session: Pi built-ins restricted to read-only (`read`/`grep`/`find`/`ls` via `allowedToolNames` — **no bash**, see decision 5), plus custom tools `memory_search`, `recall_actions` (reads recent objective events/L2), `speak`, `surface_observation`, `hand_to_executor()` (no payload — see decision 1), `pause_executor(reason)`, `resume_executor()`, `stop_executor(reason)`. System prompt block teaching the per-turn loop from flows.md: load L2 + recent events → classify intent (lightweight in P3 — full routing is P8) → act → speak briefly; plus handoff discipline (never claim work was dispatched without calling `hand_to_executor`). New event kinds `chat_message`, `observation`, `dispatched_to_executor`, `paused_by_chat`, `resumed_by_chat`, `stopped_by_chat` land on `objective_events` with surface routing (chat vs timeline) so TimelinePane shows control-plane/handoff events but not dialogue.

**Slice E — Executor control.** `stop_executor` = hard abort of the in-flight Pi call (wire the existing-but-uncalled `Abort` path; race-free per flows.md). `pause_executor` = halt at the next action boundary: Rust marks the executor paused; the boundary is enforced sidecar-side (gate before the next tool call / turn continuation — mechanism to be settled in the spike). `resume_executor` re-enters. Executor status (`idle`/`running_action`/`paused`/`blocked`) lands in L2 so the chat-shadow can read it before invasive operations (flows.md coordination rules).

**Slice F — Dual-surface wiring.** All chat panes (general + scoped) send to the chat-shadow session — one input box, no captain-visible target (`liveBinding.sendPrompt` re-points; the scoped-chat primer pattern carries over unchanged but primes the chat-shadow instead of the executor). Streaming state splits per organ; chat renders `chat_message`/`observation`/dialogue only; TimelinePane stays executor-work-only; pause/resume affordance in the NOW strip reflects `paused_by_chat` state; handoffs are visible as `dispatched_to_executor` rows. The ordinal turn-tagging on the executor session (`paneForOrdinal`) is retired once scoped chats move over.

## 4. Decisions (open questions resolved 2026-06-12)

1. **How work reaches the executor: verbatim conversation injection, chat-shadow decides *when*, mechanism decides *what*.** One input box; all captain input goes to the chat-shadow. Dispatch is a **no-payload `hand_to_executor()` tool** — the model never writes the forwarded instruction. On handoff, Rust injects the **verbatim conversation slice since the last handoff** (both speakers — the chat-shadow's replies are promises the executor must know about) into the executor as a clearly fenced user-role block (the `objective_prompt.rs` rehydration pattern): via `prompt` when idle, via the existing `followUp`/steer path when running (`runtime-manager.ts:403-412` — the same delivery mechanics scoped chats use today). A watermark per handoff guarantees nothing is injected twice; each handoff records a `dispatched_to_executor` event so routing failures are observable on the timeline. Rationale: today's scoped chats prove the words already travel verbatim into the executor's context — P3 splits the two jobs that single turn does (answering moves to the chat-shadow, reading the recorded substrate; only dispatched work crosses over). An **idle fast-path** (frontend sends straight to the executor when idle) is a permitted optimization *only because* it is byte-identical to the injected slice by construction — the target is resolved at send time by Rust, not by the frontend's view of streaming state. Slice distillation (plan items, notes instead of raw transcript) is the P8 upgrade; verbatim is the honest floor.
2. **Scoped chats fold into the chat organ.** The primer pattern (action context prepended on first send) carries over unchanged but targets the chat-shadow session. This removes ordinal turn-tagging (`paneForOrdinal`) from the executor path entirely. Known behavioral difference, accepted: the chat-shadow answers from the *recorded* substrate (events, outcomes, L2), not the executor's full in-context memory — equivalent for well-narrated work, and it makes narration quality directly observable.
3. **`sessions.role` column, not an `attention_threads` table.** Two roles, each 1:1 with a session row; the role column plus a manager-enforced invariant (one *active* chat session per agent) covers P3. `attention_threads` earns its keep when threads carry their own state (observer threads, post-P3); backfill from `sessions.role` then. Existing sessions migrate as `executor`.
4. **Second live-state channel: `agent-chat-state-{id}` alongside `agent-state-{id}`.** Independent `stateVersion` streams — chat can never clobber the executor view, no debounce churn across organs, and the executor channel stays byte-identical to today so the timeline/NOW strip/MON-124 surfaces need zero changes. Consumers don't overlap (ChatThread renders dialogue, TimelinePane renders work).
5. **No bash for the chat-shadow in P3.** A read-only command-pattern gate over bash is a leaky parsing problem (shells compose); an absent tool can't leak. `read`/`grep`/`find`/`ls` + `recall_actions` + `memory_search` cover the chat-shadow's actual question surface. Structured `git_status`/`git_diff`-style custom tools (not bash) are a fast-follow, not a P3 blocker.
6. **Pause mechanism: the spike decides; pre-tool-call gate preferred.** Order of preference: (1) a gate in the tool-execution path (paused flag checked before each tool call; turn stays alive; resume releases the gate) — exact action-boundary semantics; spike must confirm Pi exposes the hook and that a parked tool promise doesn't break streaming/timeouts; (2) fallback: abort-and-checkpoint (abort the turn, re-prompt with "you were paused mid-action X" on resume) — works with existing plumbing but resume is a new turn. Cooperative pause via tool results is ruled out. `stop_executor` is the existing `Abort` protocol path, which today has no caller — wire it.
7. **Chat-shadow model + lifecycle: same model as the executor; lazy; agent-lifetime.** Same model because coherence ("the same mind") is the product's signature claim and dialogue turns are the cheap part — a config knob later if cost bites. Lazily spawned on first chat input (flows.md entry conditions all start "when the captain opens chat"); survives executor restarts **and** new executor sessions (MON-127: a new working context is not a new conversation — don't conflate the lifetimes); crash recovery is respawn-on-next-message (its substrate is in SQLite); destroyed with the agent.
