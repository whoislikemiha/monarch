# MON-128 — P3: Two-organ shadow (chat-shadow + executor via two Pi sessions per agent)

> Research plan. Design sources: `thoughts/design/shadow-cognition/attention.md` (§ captain experience, § two surfaces, § thread types, § tool taxonomy by thread), `flows.md` (§ chat-shadow per-turn loop, § coordination, § conversation entry conditions), roadmap-v2 § P3. Read those before implementing — the tool lists, event kinds, and pause semantics below are lifted from them.

## 1. Summary

P3 splits a working shadow into two concurrent Pi sessions expressing one identity: an **executor** (full toolset, acts on the world, narrates the timeline) and a **chat-shadow** (read/direct/control only — answers the captain from L2 + the objective event log, and can pause/resume/stop the executor). Both sessions share the substrate (L1 identity via shadow-oath, L2 `agent_working_memory`, L3 memories, objective events); coherence comes from the substrate, not a shared context window.

Two findings reshape the expected scope:

- **The Pi-concurrency risk looks smaller than feared.** Pi SDK has no module-level singletons; `AgentSession` and `SessionManager` are instance-scoped; an upstream concurrent-session test suite exists (`pi/packages/coding-agent/test/agent-session-concurrent.test.ts`); per-session `allowedToolNames`/`excludedToolNames` and `customTools` already support a differently-armed second session. The sidecar's 1-session-per-agent is a keying convention (`Map<agentId>`), not an architectural limit. A short spike still goes first, but it's confirmation, not invention.
- **The dual-surface UI already exists (MON-124).** `TimelinePane` is mounted by default in `SoloWorkspace` as a sibling tile to chat; chat is de-tooled (`ToolActivityChip` links to timeline rows); scoped chats spawn from action cards. P3's frontend work is *re-pointing chat at the chat-shadow session* and splitting streaming sources — not building surfaces.

The bulk of the work is therefore in **Rust**: every layer of `src-tauri/src/agent/` assumes one session per agent (session_map, live state, event dispatch, persistence, keeper, kill). That's the real lift.

## 2. Relevant files and areas

### Sidecar (Node, Pi host)
- `sidecar/src/runtime-manager.ts` — sessions keyed by `agentId` in `Map<string, ManagedSession>` (~line 72); create replaces any existing session (~106); each session's listener tags events with `agentId` (~237); tools injected per-session via `customTools` (~144–155); `SessionManager.inMemory(cwd)` per session (no disk persistence, Rust owns history). The keying and event tagging are the two things that must become role-aware.
- `sidecar/src/protocol.ts` + `src-tauri/src/sidecar_protocol/commands.rs` — `create_session` / `prompt` / `abort` / `destroy_session` are all `{agent_id}`-addressed; need a session-role discriminator. `Abort` exists in the protocol but has no Rust caller today.
- `sidecar/src/shadow-oath.ts` — system prompt builder; both sessions must render the same L1 identity, with organ-specific behavior blocks (executor narration rhythm vs chat-shadow brevity/loop).
- `sidecar/src/memory-tools.ts`, `narration-tools.ts`, plan/report tools — the executor's custom tools; the pattern (closure over `agentId` + `emit`) is reusable for chat-shadow tools.
- `/Users/miha/pro/pi` — `packages/coding-agent/src/core/agent-session.ts` (`allowedToolNames`/`excludedToolNames` ~173–175), `session-manager.ts`, and the concurrent test suite — the spike's reference material.

### Rust (the heavy side)
- `src-tauri/src/agent/manager.rs` — `session_map: HashMap<agent_id, session_id>` (~59–61) is the load-bearing 1:1 assumption; `live_states` keyed by agent_id only; `spawn()` (~565), `new_session()`/`switch_session()` (~915–1055), `kill()` (~858) all single-session.
- `src-tauri/src/agent/event_handler.rs` — `get_session_id(agent_id)` (~31) resolves the *one* session for persistence; dispatch (~90–237) must learn which organ an event came from.
- `src-tauri/src/agent/persist/` — single-consumer pipeline; `build_persist_commands()` writes to the resolved session_id; must route per source session.
- `src-tauri/src/agent/keeper.rs` + `manager.rs::dispatch_keeper_run` — keeper slices `list_agent_messages_since_internal(agent_id, …)` with **no session filter**; chat turns would pollute the distillation slice.
- `src-tauri/src/agent/state.rs` — `LiveAgentState` assembly; one snapshot topic `agent-state-{id}`.
- `src-tauri/src/db/schema.rs` + `db/sessions.rs` — sessions table (with MON-127 `parent_session_id`, `title`); new role column / attention_threads table follows the ALTER TABLE migration convention.
- `src-tauri/src/agent/commands.rs` + `websocket/dispatch.rs` — command surface to mirror for the chat organ.

### Frontend (mostly wiring)
- `src/lib/workspace/SoloWorkspace.svelte` — tiles `[TIMELINE_TILE, "general", …scopedChats]`; already the dual surface.
- `src/lib/workspace/ChatThread.svelte` + `liveBinding.svelte.ts` (`sendPrompt` ~219) — where prompts get routed; today all panes share the one Pi session, turns tagged to panes by ordinal (`chatStore.paneForOrdinal`).
- `src/lib/workspace/TimelinePane.svelte` / `timelineStore.svelte.ts` / `timelineModel.ts` — shipped; needs to stay executor-only (it reads `objective_events`, which chat-shadow events will also land on — surface routing matters here).
- `src/lib/toolbox/liveAgentStore.svelte.ts` — single `isStreaming` per agent; needs per-organ streaming distinction.

## 3. What needs to change

Proposed slices (each independently testable, per the phase rule):

**Slice A — Pi-concurrency spike (timeboxed; goes first).** In the sidecar, spawn two `AgentSession` instances for one agent (same cwd, distinct `SessionManager.inMemory`, distinct tool sets), prompt both concurrently, and verify: event interleaving on stdout is correctly per-session-tagged, no shared-state bleed (extensions, resource loader, model registry), abort on one doesn't disturb the other. Output is a go/no-go note + any constraints discovered (e.g. memory footprint, event ordering). Roadmap-v2 names this the one real technical risk; everything later rides on it.

**Slice B — Session roles in the substrate.** Persist the organ: either `sessions.role` (`executor`/`chat`) via ALTER TABLE, or an `attention_threads` table mapping agent → role → session (design doc names the latter; decide at impl time — see open questions). Sidecar protocol grows a role discriminator on `create_session`/`prompt`/`abort`/`destroy_session`; runtime-manager keys sessions by `(agentId, role)` and tags emitted events with the role. Rust `session_map` becomes role-aware. Migration note: every existing session is `executor`.

**Slice C — Rust plumbing for the second session.** The single-session assumptions list, worked through: event_handler resolves session by (agent, role) from the event tag; persist pipeline writes chat turns to the chat session's rows; keeper slice and classifier gate to executor-session content only; `kill()` tears down both organs; `new_session`/`switch_session` (MON-127 semantics) operate on the executor session and leave the chat organ alone. Live state: keep `agent-state-{id}` as the executor stream and add a parallel chat-state channel (or a role field on items — see open questions). The chat session is spawned lazily when the captain opens chat (per flows.md entry conditions), not at agent spawn.

**Slice D — Chat-shadow session: tools + prompt.** A read/direct/control session: Pi built-ins restricted to read-only (`read`/`grep`/`find`/`ls` + read-only bash — enforcement via `allowedToolNames`/`excludedToolNames` plus whatever bash gating is feasible; see open questions), plus custom tools `memory_search`, `recall_actions` (reads recent objective events/L2), `speak`, `surface_observation`, `pause_executor(reason)`, `resume_executor()`, `stop_executor(reason)`. System prompt block teaching the per-turn loop from flows.md: load L2 + recent events → classify intent (lightweight in P3 — full routing is P8) → act → speak briefly. New event kinds `chat_message`, `observation`, `paused_by_chat`, `resumed_by_chat`, `stopped_by_chat` land on `objective_events` with surface routing (chat vs timeline) so TimelinePane shows control-plane events but not dialogue.

**Slice E — Executor control.** `stop_executor` = hard abort of the in-flight Pi call (wire the existing-but-uncalled `Abort` path; race-free per flows.md). `pause_executor` = halt at the next action boundary: Rust marks the executor paused; the boundary is enforced sidecar-side (gate before the next tool call / turn continuation — mechanism to be settled in the spike). `resume_executor` re-enters. Executor status (`idle`/`running_action`/`paused`/`blocked`) lands in L2 so the chat-shadow can read it before invasive operations (flows.md coordination rules).

**Slice F — Dual-surface wiring.** Chat panes send to the chat-shadow session (`liveBinding.sendPrompt` grows a target); streaming state splits per organ; chat renders `chat_message`/`observation`/dialogue only; TimelinePane stays executor-work-only; pause/resume affordance in the NOW strip reflects `paused_by_chat` state. Reconcile MON-124's scoped chats with the chat organ (see open questions).

## 4. Open questions

1. **How does work reach the executor in P3?** Today the composer prompts the executor directly. In the target model the captain only talks to the chat-shadow — but the routing classifier and plan-manipulation tools are explicitly P8. Interim options: (a) chat-shadow gets one thin `direct_executor(instruction)` tool and *all* captain input goes through it; (b) the composer keeps a target (work → executor, chat → chat-shadow), preserving today's direct path; (c) heuristic: direct prompts when executor idle, chat-shadow when running. (a) is purest but puts a hop+latency on every dispatch; (b) is least risk but leaks the two-organ seam into the UX the design says should be invisible. **Needs a call before Slice D.**
2. **Scoped chats (MON-124) vs the chat organ.** Scoped chats currently share the executor session with ordinal-tagged turns. Do they all become chat-shadow turns with context primers (cleanest — removes turn-tagging from the executor session), or stay as-is alongside the chat organ? Leaning: fold them into the chat-shadow.
3. **`attention_threads` table vs `sessions.role` column.** The design doc names `attention_threads`; a role column is smaller and fits the MON-127 session model. A role column plus a uniqueness rule (one live chat session per agent) may be all P3 needs; `attention_threads` earns its keep when observer threads (post-P3) arrive.
4. **Live-state channel shape.** Second event channel (`agent-chat-state-{id}`) vs one merged snapshot with per-item organ tags. Second channel keeps `stateVersion` reconciliation simple and chat clobbering impossible; merged state keeps the frontend store count down.
5. **Read-only bash enforcement.** `allowedToolNames` can exclude write/edit, but bash is one tool — read-only-ness needs either a command-pattern gate (sidecar-side wrapper) or dropping bash from the chat-shadow in P3. Dropping it is safer and cheaper; the design doc lists it as desirable, not essential.
6. **Pause mechanism.** "Halt after current tool call" needs a concrete Pi hook — abort-and-checkpoint, a gate in the tool-execution path, or an extension hook. Spike (Slice A) should answer which is viable; flows.md only fixes the semantics, not the mechanism.
7. **Chat-shadow model + lifecycle.** Same model as the executor or a cheaper tier? And does the chat session survive executor restarts / get destroyed on idle? Suggest: same model (identity coherence), lazily spawned, destroyed with the agent — revisit if cost bites.
