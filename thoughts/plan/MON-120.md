# MON-120 — P6 Slice B: complete_quest(report) tool + executor prompt

Research plan. Planning only — no implementation here.

## Summary

P6 turns a closed quest into a first-person record. Slice A (MON-119, merged)
built the storage substrate: the `quest_reports` table, the
`WriteQuestReportPayload` DTO, a `PersistCommand::WriteQuestReport` pipeline
variant, and a Tauri/WebSocket command surface — all currently producer-less.

Slice B builds the producer. The executor shadow gets a `complete_quest(report)`
tool. When it finishes a quest it calls the tool with a structured first-person
payload (summary, outcome, decisions, learned, artifacts, open_threads,
reflection, grade). The sidecar emits an event; Rust persists the report through
the single-consumer pipeline and — per the design decision taken during
planning — also **closes the quest**: it transitions `quest_nodes.status` and
runs the same side effects the captain's `db_update_quest` path runs today
(a `status_change` quest event, clearing the agent's current-quest pointer, and
dispatching the MON-103 quest-close Keeper run). A new system-prompt block in
`shadow-oath.ts` teaches the shadow the payload shape and when to emit it. The
"report-on-close" contract is enforced by the tool doing both in one atomic
pipeline step, plus prompt guidance — not by a schema constraint.

  prompt. Has a `## Tools` list (lines ~104–119) and dedicated instructional

- `sidecar/src/protocol.ts` — wire types. `AgentEventEnvelope` (~211) is the

  typed (as narration/plan events appear to be), no change is needed.

### Rust

## What needs to change

### 1. New sidecar tool module

A new module (modeled on `narration-tools.ts`) exporting a factory that returns
a single `complete_quest` tool. The tool's `report` parameter is a structured
object:

- `summary` — string, one-to-few sentences.
- `outcome` — enum: `done | blocked | abandoned | partial`.
- `decisions` — array of `{ decision, rationale? }`.
- `learned` — array of strings (the shadow's own suggestions to the Keeper).
- `artifacts` — array of `{ file, role }` (role e.g. created / modified /
  documentation).
- `open_threads` — array of strings.
- `reflection` — string, brief.
- `grade` — string, self-suggested (Keeper/captain may override later).

Field caps follow the trim-don't-reject pattern from `plan-tools.ts` (overlong
input is truncated so the tool call never fails). On execute, the tool emits a
single `event` envelope with a new inner-event tag carrying the structured
report. Registered in `runtime-manager.ts` next to the narration/plan tools.

### 2. Rust inbound event

A new `InnerEvent` / `KnownInnerEvent` variant for the quest-report event,
wired through the `From` mapping, `inner_event_tag`, and `apply_event`
(`NoOp` — no live-state mutation). The variant carries the structured report.

### 3. Pipeline command + apply path

A new `PersistCommand::CompleteQuest` variant is added (distinct from Slice A's
producer-less `WriteQuestReport` — see resolved decisions). It carries the
`agent_id`, `quest_id`, the structured report, and the `outcome`.
`build_persist_commands` gets a match arm for the new event. When a
`current_quest_id` is present it pushes the `CompleteQuest` command, whose apply
arm performs in strict order:

1. **Write the report** via `upsert_quest_report_internal` (serializing the
   structured report to the JSON `payload` column). This must happen first so
   the quest-close Keeper tick (Slice D) sees it.
2. **Transition quest status** for terminal outcomes — `done → status 'done'`
   (+`completed_at`), `abandoned → status 'abandoned'` (+`abandoned_at`) — via
   `update_quest_internal`. Non-terminal outcomes (`blocked` / `partial`) write
   the report but leave the quest status unchanged (see open questions).
3. **Run quest-close side effects** by reusing `handle_quest_update_side_effects`
   (status_change event, clear current-quest pointer, dispatch the quest-close
   Keeper run). The consumer obtains `Arc<AgentManager>` via
   `AppHandle::state()` from its `app_handle` slot.

The single-consumer pipeline guarantees steps 1→3 run in order with no
interleaving — that is what makes "report written before Keeper fires"
structural rather than best-effort.

If no `current_quest_id` is set, the event is dropped with a log line (same
posture as `MemorySuggestion` in `build_persist_commands`).

`CompleteQuest` carries a real `agent_id` in `PersistCommand::agent_id()`
(unlike the producer-less `WriteQuestReport` variant, which returns `""`) so a
persist failure desyncs the correct agent.

For step 3, `handle_quest_update_side_effects` is reused **unchanged**. It gates
the Keeper dispatch on `transitioned_to_done`, so `outcome = done` fires the
quest-close Keeper run; `outcome = abandoned` closes the quest and records the
`status_change` event but does **not** fire a Keeper tick. A lighter
abandonment-distillation pass (per distillation.md) is left as a clean
follow-up — extending that trigger would also change the captain's
`db_update_quest` behavior and is out of Slice B scope.

### 4. Executor system prompt

`buildSystemPrompt` in `shadow-oath.ts` gains:
- a `complete_quest` line in the `## Tools` list;
- a new `## Quest Report` instructional block teaching the payload shape, the
  meaning of each field, the `outcome` values, and the emission rule: call
  `complete_quest` exactly once, when work on the quest is finished, as the
  final action on that quest. The block should make clear the report is the
  shadow's own first-person voice and that `grade` is a self-suggestion.

### 5. Tests

Rust unit tests (Vitest is not the right layer here — the logic is Rust):
- New event deserializes from wire JSON into the `InnerEvent` variant.
- `build_persist_commands` produces the quest-close command for the event when
  a `current_quest_id` is present, and drops it (log only) when absent.
- Apply-path ordering: the report row exists before the status transition is
  observable — i.e. report write precedes status write.
- `outcome = done` transitions status to `done`; `outcome = abandoned`
  transitions to `abandoned`; `outcome = blocked` / `partial` leave status
  unchanged but still write the report.
- The quest-close path records a `status_change` quest event and clears the
  agent's current-quest pointer (reusing `handle_quest_update_side_effects`,
  so this is mostly a wiring assertion).
- `apply_event` returns `NoOp` for the new event (no live-state churn).

Sidecar: a light test that the tool emits a well-formed envelope is optional;
the narration/plan tools have no such tests, so matching that precedent (no
sidecar test) is acceptable.

## Resolved decisions

- **New `CompleteQuest` variant.** A distinct `PersistCommand::CompleteQuest` is
  added rather than overloading Slice A's producer-less `WriteQuestReport`.
  `WriteQuestReport` is left in place for a possible future pure-write producer.
- **Non-terminal outcomes are allowed.** `complete_quest` accepts `outcome` of
  `blocked` / `partial`: the report is written and the quest is left open
  (status unchanged, no Keeper close-tick). The tool is not strictly a
  quest-*close* tool — it always records the report, and additionally closes
  the quest for terminal outcomes.
- **Abandonment fires no Keeper tick (for now).** `handle_quest_update_side_effects`
  is reused unchanged; its Keeper dispatch stays gated on `transitioned_to_done`.
  Abandonment closes the quest and records the `status_change` event but does
  not run a Keeper pass. A lighter abandonment-distillation pass is a clean
  follow-up, deliberately out of Slice B scope.

## Open questions

1. **Re-invocation / idempotency.** `quest_reports` has `UNIQUE(quest_id)` with
   upsert, so a second `complete_quest` call cleanly overwrites the report. But
   the second call would also re-run the status transition + side effects
   (re-dispatching the Keeper). Should the apply path no-op the close side
   effects when the quest is already terminal? (The existing
   `handle_quest_update_side_effects` already guards on
   `before_status == after_status`, so this may be handled for free — confirm.)
2. **Inner-event tag name.** Proposed `quest_report`; `quest_completed` or
   `complete_quest` also reasonable. Cosmetic — pick at impl time.

## Out of scope

- Captain UI / report renderer in the P5 quest detail panel — Slice C.
- Keeper consuming `quest_reports.payload` on quest-close ticks, and
  auto-populating `distilled_by_keeper_run_id` — Slice D.
- Any schema change to `quest_reports` — Slice A shipped the table.
- Writing the report's `grade` / `summary` back onto `quest_nodes` — the
  roadmap keeps the quest node's own grade/summary captain-edited (P5); the
  report is a separate artifact.
- A `suggest_memory` executor tool — distillation.md mentions it, but it is a
  separate cognition surface, not part of P6.
