# MON-122 — P6 Slice D: Keeper consumes the first-person quest report

Research plan. The final P6 slice — fold the report into the Keeper's input
on quest-close and write the run id back onto the report row.

## Summary

P6 Slice A (MON-119) shipped `quest_reports` storage. Slice B (MON-120)
shipped the producer (`complete_quest(report)` + the pipeline path that
writes the report and closes the quest atomically). Slice C (MON-121) shows
the report to the captain.

Slice D closes the loop: when MON-103's quest-close Keeper trigger dispatches
a run for a quest that has a first-person report, the slice the Keeper
consumes now includes that report alongside the raw stream. After the run
completes successfully, `quest_reports.distilled_by_keeper_run_id` is set to
the run id via the single-consumer persistence pipeline.

This is the "noticeably better claims than P2's report-less Keeper" half of
the P6 milestone (roadmap §P6 test scenario).

## Relevant files and areas

### Rust

- `src-tauri/src/agent/manager.rs` `render_keeper_slice` (~1089–1121) — the
  pure-function slice renderer. Today: prior summary → related memories →
  raw stream. New: an optional quest-report section between related memories
  and the raw stream.
- `src-tauri/src/agent/manager.rs` `dispatch_keeper_run` (~290–424) — chooses
  the trigger anchor, fetches messages + related memories, renders the slice,
  inserts the keeper run row, and ships the `SidecarCommand::KeeperRun`.
  Quest-report fetch lands here; only the `QuestClose` arm pulls it.
- `src-tauri/src/agent/event_handler.rs` `handle_keeper_result` (~572–726) —
  after the successful `CompleteKeeperRun` send, on `trigger == "quest_close"`
  with a resolved provenance quest id, enqueues the attribution command.
- `src-tauri/src/agent/persist.rs` — new `PersistCommand::AttributeQuestReport`
  variant; apply path calls the new DB method, logs a one-line warning when
  the no-op case fires (report-less quest-close run).
- `src-tauri/src/db.rs` — new
  `attribute_quest_report_to_keeper_run_internal(quest_id, run_id)` method.
  Idempotent `UPDATE`, returns whether a row was touched. No FK violation
  risk: the column is nullable and `ON DELETE SET NULL`, so re-attribution is
  a plain rewrite.
- `src-tauri/src/db.rs` `get_quest_report_by_quest_internal` (~3520) — read
  helper already shipped in Slice A; Slice D is its first non-UI caller.

### Sidecar

- `sidecar/src/keeper.ts` — entry point consumes the slice text verbatim
  (`user`-role message in the Keeper LLM call). No schema change here; the
  report payload is already JSON text from Slice B's serialization, so a
  marker section header is enough for the LLM to parse it as first-person
  context.

## What needs to change

### 1. `render_keeper_slice` parameter

Add `quest_report: Option<&str>` (last parameter). When `Some` and trimmed
non-empty, emit a `## QUEST REPORT (first-person from the executor)` section
between the related-memories block and the raw activity block. Empty / whitespace
payloads are dropped silently so an upstream coding regression doesn't surface
a header above nothing.

### 2. `dispatch_keeper_run` — fetch on quest-close

Right after `let kept = ...` and before the slice render, derive a
`quest_close_report: Option<String>` by matching on `&trigger`:

- `KeeperRunTrigger::QuestClose { quest_id, .. }` → call
  `db.get_quest_report_by_quest_internal(quest_id)` and take `.payload`.
- `KeeperRunTrigger::Continuous` → `None` (even when the agent has a current
  quest with a report — continuous runs are not closing-events).

Failures from the report fetch are logged and degrade to `None` so the run
still proceeds against the raw stream.

### 3. `PersistCommand::AttributeQuestReport` + apply

New variant `{ agent_id, quest_id, run_id }`. `agent_id()` returns the real
id so a desync flags the right agent (contrast with `WriteQuestReport` which
returns `""`). Apply calls the new DB method; logs a one-line warning when
the update touches zero rows (the report-less close path). Never errors on
the no-op case.

### 4. `handle_keeper_result` — enqueue attribution

After the successful `CompleteKeeperRun` enqueue, on
`trigger == "quest_close"` with `run_row.quest_id` resolved, send
`AttributeQuestReport`. The persistence pipeline serializes the writes so
attribution lands after the run row's completion is recorded.

### 5. DB method

`attribute_quest_report_to_keeper_run_internal(quest_id, run_id) -> bool`.
One `UPDATE quest_reports SET distilled_by_keeper_run_id = ?1 WHERE quest_id = ?2`.
Returns `n > 0`. Touches no other columns — `updated_at` is reserved for
content changes, attribution is metadata.

### 6. Tests

`src-tauri/src/agent/manager.rs::tests`:
- `render_keeper_slice` with `Some(payload)` includes the new section header
  and the payload text; the `## RECENT ACTIVITY` marker is still emitted.
- `render_keeper_slice` with `None` does not emit the section header.
- `render_keeper_slice` with whitespace-only payload does not emit the
  header (defensive).

`src-tauri/src/agent/persist.rs::tests`:
- Apply `AttributeQuestReport` after seeding a report + a keeper run; assert
  the report's `distilled_by_keeper_run_id` is set.
- Apply twice with different run ids; assert the second attribution wins
  (idempotent rewrite, no uniqueness violation).
- Apply for a quest that never produced a report; assert `Ok(())` and no
  report row is created.

## Resolved decisions

- **Continuous runs ignore reports.** Even when a current quest is set and
  has a report, a continuous-trigger Keeper run does not include it. A
  continuous run is mid-quest compaction; the report's job is to summarize
  the closing event for a quest-close run specifically. Mixing them would
  pollute mid-quest compactions with stale framing.
- **Pipeline write for attribution.** The attribution rides the persistence
  pipeline rather than a direct DB write in `handle_keeper_result` so it
  serializes cleanly with the keeper-run completion. This is the same
  posture as the `InsertMemory` + `CompleteKeeperRun` sequence the result
  handler already enqueues.
- **No-op on missing report is allowed.** A quest-close run can fire on a
  quest that was captain-closed (via `db_update_quest`) without an executor
  report. The apply logs but does not error. The pipeline always sends the
  command on `quest_close` triggers; the apply absorbs the empty case.
- **No system-prompt change.** A section header in the user-message slice is
  enough for the LLM to recognize first-person framing; a Keeper prompt tier
  change is a deliberate roadmap follow-up if calibration shows it helps.

## Out of scope

- Pretty-printing the report JSON into a markdown rendering. The raw payload
  is already JSON text from Slice B's serialization. The LLM consumes JSON
  fine; spending parse work in Rust to re-render markdown was deemed not
  worth it until eval shows it matters.
- Lighter abandonment-distillation pass. Slice B carries this deferral
  (Keeper still gated on `transitioned_to_done` in
  `handle_quest_update_side_effects`).
- Captain-edited grade write-back onto `quest_nodes.grade`. Roadmap keeps
  the quest node's grade captain-edited (P5); the report is its own artifact.
