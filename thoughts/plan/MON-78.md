# MON-78 — Provider-aware thinking levels + per-model defaults

## Summary

Monarch currently treats "thinking level" as a single six-valued string (`off | minimal | low | medium | high | xhigh`) shared across every provider and every model. That enum is both wider than what Pi SDK actually accepts (Pi's `ThinkingLevel` is `minimal | low | medium | high | xhigh`, with no `off`) and narrower than what providers expose natively (Anthropic adaptive models top out at `max` on Opus 4.6, Gemini caps at `HIGH`, LM Studio has no thinking at all, OpenAI uses per-model `reasoning_effort`). The mismatch causes a live bug: passing `"off"` to Pi makes it fall through to its default switch case — on adaptive Anthropic models that default returns `"high"`, so the UI's "off" silently applies high thinking. The plan is to replace the shared enum with a provider-aware level representation, let the UI render only the native levels each model supports, give every model a configurable default via a config source, and ensure a real "off" state means the sidecar omits reasoning entirely.

## What needs to change

### 1. Replace the flat level enum with a provider-aware level descriptor

Introduce a single source of truth — something like `src/lib/thinking.ts` (mirrored in `sidecar/src/thinking.ts`) — that describes, per `(provider, modelId-pattern)` pair:

- The set of supported levels in provider-native terms (e.g. Anthropic adaptive Opus 4.6 → `low | medium | high | max`; Sonnet 4.6 → `low | medium | high`; Gemini → `MINIMAL | LOW | MEDIUM | HIGH`; OpenAI / OpenRouter → `low | medium | high` with per-model `reasoning_effort` overrides; Anthropic non-adaptive → token-budget tiers; LM Studio → not supported).
- How each native level maps onto a Pi-canonical `ThinkingLevel` value when sent on the wire.
- The default level for that model.

Keep this as data, not a sea of `if` branches. The UI consults it; the sidecar consults the same table to convert the operator's selection back to Pi's accepted `ThinkingLevel` (or to `undefined`).

### 2. Make "off" a first-class absence rather than a string

The canonical on-wire value for "don't reason" must be "no level at all". That likely means:

- Extend `SetThinkingLevel` in `sidecar_protocol.rs` / `protocol.ts` so the level is optional (`Option<String>` / `string | null`).
- In `runtime-manager.ts`, when the incoming level is absent or sentinel-off, do not pass a `ThinkingLevel` to Pi — either skip the call or reset to `undefined` (confirm Pi's API supports "unset reasoning" mid-session; if not, we reset by cycling state).
- In the DB and Rust defaults (`agent/manager.rs:386` currently hardcodes `"medium"`), replace the fallback with a lookup into the new config so the default flows from one place instead of two.

### 3. Per-model defaults from a config source

Add a user-editable config file — a natural home is `~/.config/monarch/thinking.toml` (or `.json`) alongside the existing prompt overrides directory. Shape:

- Keyed by `(provider, modelId)` with pattern support for model families (e.g. `anthropic/claude-opus-4-6*`).
- Fields: `default` level (provider-native or `off`), optional override of the supported-levels list, optional per-level token-budget hints for non-adaptive token-based models.
- Ships with a sensible built-in table so a fresh install works without the file. File, when present, merges over the built-in.

On the Rust side, load this at startup and expose it to the sidecar either via a one-shot handshake message or by inlining resolved defaults into each `CreateSession` / `SetModel` command. The latter is simpler — keep Rust as the owner of config, sidecar stays stateless about user preferences.

### 4. UI changes driven by the current model

All three pickers (SpawnForm/ModelSelector, EditAgentDialog, AgentControls) should:

- Render only the supported levels for the current `(provider, model)`, with provider-native labels.
- Include a consistent "off" option (except where unsupported — e.g. LM Studio hides the whole picker).
- When model changes, reset the selected level to the config default for the new model, or clamp to the nearest supported value if the user's current choice is invalid.
- Replace the three hardcoded copies of the level array with imports from the shared descriptor module.

### 5. Rust ↔ sidecar plumbing

- Regenerate `bindings.ts` after any Rust type change (`cargo run -- --export-bindings` from `src-tauri/`).
- Keep the stored DB value human-readable — prefer storing the provider-native string (e.g. `"max"`, `"HIGH"`, `"off"`) rather than a Pi-canonical string, so inspection / manual edits match what users see in the UI. The sidecar is responsible for the final translation to Pi's `ThinkingLevel`.

### 6. Docs

- Update `ONBOARDING.md` thinking-level section to describe the provider-aware model and point at the new config file.
- Add a short "Thinking levels" section to `CLAUDE.md` under Rules & Gotchas, calling out the config file location and that `"off"` means "no reasoning on the wire".

## Open questions

1. **Storage format** — store the provider-native label (e.g. `"max"`, `"HIGH"`) or a Pi-canonical label (`"xhigh"`)? Native is more honest in the UI and in DB inspection, but means more translation on the sidecar side and makes moving a template across models awkward. Default recommendation: native, because it matches what the user picked and the sidecar already owns the translation anyway.
2. **Mid-session level switches on Pi** — does `AgentSession.setThinkingLevel` accept an `undefined` / off value to truly turn reasoning off mid-session, or do we need to recreate the session / issue a no-op that unsets it? Needs a quick spike against Pi.
3. **Anthropic non-adaptive models (pre-4.6)** — do we want to expose token-budget tiers as discrete levels (`minimal/low/medium/high` with Pi's default budgets) or just hide thinking for them? Simplest is the former since Pi already maps them; confirm whether any of those models are still worth supporting in Monarch today.
4. **Config file format** — TOML (matches other Rust-side config idioms) or JSON (matches how the frontend could read it directly)? If Rust stays authoritative, TOML is fine. If the frontend ever needs to read it without going through Rust, JSON is easier.
5. **Per-agent override vs global default** — today every agent stores its own `thinking_level`. Is the global config default just the seed at creation time, or should existing agents without an explicit override re-pick the default when the config changes? Recommend: config seeds on create; agents carry their own value afterwards.
6. **OpenRouter model families** — since OpenRouter proxies many upstreams, do we want the per-model support matrix keyed by the upstream provider (e.g. detect `anthropic/...` route and apply Anthropic rules) or keep OpenRouter as its own bucket with a simple `low/medium/high`? Pi handles this with `reasoningEffortMap`, so our config can piggyback on the same idea.

## Out of scope

- Migrating historical `thinking_level` values in existing SQLite rows — thinking is applied per chat going forward.
- Custom operator-defined thinking ladders beyond what the config file exposes for defaults / supported-set overrides.
- Dynamic "bump thinking when stuck" heuristics.
- Fine-grained per-provider token-budget sliders for non-adaptive Anthropic models beyond Pi's built-in mapping.
- Changes to `agent_templates` semantics beyond storing the new level representation.
