# MON-116 — P5 Slice A: quest metadata and manual-editor backend

Linear: [MON-116](https://linear.app/monarch-commander/issue/MON-116/p5-slice-a-quest-metadata-and-manual-editor-backend)

## Goal

Land the backend contract for P5 rich quests. After this slice, Monarch can
persist quest scope/direction/rationale, write semantic manual-editor events,
and attach external references to quests. The captain-facing editor UI lands in
a later slice.

## Context

P4 made the execution timeline action-shaped. P4b added the durable intended
route through `quest_plan_items`. P5 enriches the quest object itself: quest =
what/why, execution plan = intended how, coherent action = actual doing.

Existing `quest_nodes` already has `status`, `grade`, `worktree_path`, and
`summary` from MON-83. This slice should not rewrite the base table or invent a
parallel lifecycle. It should add only the missing rich fields and reference
storage through idempotent migrations.

## Scope

1. Add idempotent `quest_nodes` migrations for:
   - `scope`
   - `current_direction`
   - `rationale`
   - `fork_parent_id` (defined for P10, no fork behavior yet)

2. Add quest external-reference storage:
   - `quest_refs` table keyed by id
   - `quest_id`, `ref_type`, `label`, `target`, `metadata_json`, `created_by`,
     `created_at`, `updated_at`
   - ref types are stored as strings so UI can add new kinds without schema
     churn; v0 validates only obvious required fields.

3. Extend exported Rust DTOs:
   - `QuestRow` includes new rich fields.
   - `QuestRefRow`, `CreateQuestRefPayload`, `UpdateQuestRefPayload`.
   - `UpdateQuestPayload` accepts rich fields for legacy/direct quest updates.
   - Add a narrower manual update payload if event emission needs rationale
     and actor semantics.

4. Add DB helpers and Tauri commands:
   - list/create/update/delete quest refs
   - manual quest metadata update that emits semantic `quest_events`
   - event note helpers for `note`, `blocker`, `blocker_resolved`, `question`,
     and `answer`

5. Add WebSocket dispatch arms for all new commands.

6. Regenerate `src/lib/bindings.ts` after exported DTO/command changes.

## Event model

Manual quest edits should write timeline-visible events when they change
semantic quest state:

- `status_change`: existing side effect path remains the status authority.
- `scope_change`: payload includes `from`, `to`, `rationale`.
- `direction_change`: payload includes `from`, `to`, `rationale`.
- `quest_rationale_change`: payload includes `from`, `to`.
- `quest_summary_change`: payload includes `from`, `to`.
- `note`, `blocker`, `blocker_resolved`, `question`, `answer`: payloads are
  small typed JSON objects with `text` or `question`/`answer`.

Default author for manual-editor commands is `captain`; actor defaults to
`monarch` unless the caller supplies a more specific label.

## Acceptance

- A quest row can store and retrieve scope, current direction, rationale, and
  fork parent.
- Updating scope/direction through the manual command records corresponding
  quest events and broadcasts quest/event notifications.
- Quest refs can be added, edited, listed, and deleted.
- Browser-mode WebSocket dispatch supports the same commands as Tauri.
- Existing quest creation/listing/tests continue to work.

## Verification

- `cargo run -- --export-bindings` from `src-tauri/`
- Focused Rust tests for migrations/helpers where the existing test structure
  makes this practical.
- `cargo check` from `src-tauri/`
- `npx svelte-check` if bindings or frontend API surfaces are touched.

## Out of scope

- Quest detail/editor UI.
- Rich attachment picker UX.
- Chat-shadow or Architect consumption of question/answer events.
- Fork/worktree behavior beyond defining `fork_parent_id`.
